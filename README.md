# nemoProject

Сервис обмена валют через Telegram: клиент подаёт заявку в Mini App,
менеджер исполняет её вручную через админ-панель. Доменный язык — в
[CONTEXT.md](CONTEXT.md), принятые решения — в [docs/adr](docs/adr).

## Запуск

Нужны Node 22+, pnpm 9 и Docker.

```sh
pnpm install
docker compose up -d      # Postgres на localhost:5432, базы nemo_dev и nemo_test
pnpm db:migrate           # применить миграции к базе разработки
cp .env.example .env      # заполнить токен бота
pnpm generate-keys        # выпустить пару ключей шифрования реквизитов в .env
pnpm seed-directories     # завести валюты, направления и сети
ln -sfn ../../.env apps/miniapp/.env   # Next читает .env из папки приложения,
ln -sfn ../../.env apps/admin/.env     # а не из корня монорепо
ln -sfn ../../.env apps/cabinet/.env   # то же у кабинета мерчанта
pnpm dev
git config core.hooksPath .githooks   # напоминание про CHANGELOG.md при коммите
```

Ссылки на `.env` обязательны, и забыть их легко: корневой файл читают
скрипты, а приложения — нет, и `pnpm dev` поднимется, но первый же
запрос ответит «Не задан TELEGRAM_BOT_TOKEN». Ссылка, а не копия, чтобы
секреты не разошлись по четырём местам; под `.gitignore` она попадает тем же
правилом, что и сам файл, — то есть в клон не приезжает и заводится
руками.

Без `pnpm seed-directories` приложение откроется, но экран обмена
скажет, что направления не заведены: справочники наполняются скриптом, а
не миграцией.

`docker compose up -d` создаёт обе базы: `nemo_dev` для разработки и
`nemo_test` для тестов. Данные лежат в томе `nemo-pgdata` и переживают
перезапуск контейнера; `docker compose down -v` стирает их вместе с ним.

Postgres поднимается в контейнере, а не устанавливается в систему,
потому что версия базы — часть окружения проекта, и она должна
совпадать у всех, кто с ним работает.

**Собран он должен быть с ICU** — так собран официальный образ, который
и стоит в `docker-compose.yml` и на серверах. Поиск по названию
мерчанта идёт с явной коллацией `und-x-icu`: базы сервиса заведены с
локалью `C`, и без неё «Оплатишка» не находится по запросу «оплат» —
обычный `ilike` регистр кириллицы не сводит. На сборке без ICU поиск в
столе менеджера откажет целиком.

## Два бота и их вебхуки

Ботов два, и это решение, а не случайность
([ADR-0005](docs/adr/0005-otdelnyy-bot-dlya-vhoda-v-adminku.md)):

- **клиентский** — его запускают покупатели, через него уходят
  уведомления о заявках. Токен лежит в обоих деплоях: клиентскому нужно
  принимать обновления, админке — отправлять сообщения.
- **бот входа** — показывает кнопку Telegram Login на странице админки.
  Его токен есть только в деплое админки, поэтому утечка клиентского
  контура не даёт подделать первый фактор входа.

Обновления оба принимают вебхуком, а не опросом: приложения живут на
serverless, где некому держать длинный опрос между запросами
([ADR-0001](docs/adr/0001-mini-app-kak-osnovnoy-interfeys.md)).

```sh
pnpm set-telegram-webhook                  # клиентский бот, по MINIAPP_URL
pnpm set-telegram-webhook --admin          # бот входа, по ADMIN_URL
pnpm set-telegram-webhook --info           # что зарегистрировано сейчас
pnpm set-telegram-webhook --admin --info
pnpm set-telegram-webhook --delete         # снять
```

Бот входа отвечает адресом админки и порядком входа на любое сообщение
в личной переписке, а не только на `/start`. Своей работы у него там
нет — но молчащий бот выглядит сломанным, и первым делом в нём начинают
искать саму админ-панель. Сотрудник, у которого вход не выходит, пишет
боту словами, а команду угадывать не приходится: её не знают как раз
те, кому бот и нужен.

Регистрация передаёт `secret_token` — `TELEGRAM_WEBHOOK_SECRET` у
клиентского бота, `ADMIN_BOT_WEBHOOK_SECRET` у бота входа, — а маршрут
сверяет его с заголовком `x-telegram-bot-api-secret-token` и без
совпадения не отвечает: адрес вебхука рано или поздно утекает, и без
секрета кто угодно сможет присылать боту поддельные обновления. Секреты
разные: боты разные, и общий связал бы их обратно.

Команду нужно повторить после каждой смены домена — Telegram шлёт
обновления по тому адресу, который ему назвали последним.

## Как посмотреть Mini App с телефона

В браузере оно не открывается вовсе: подпись `initData` проверяется
всегда, и обхода в коде нет. Полноэкранный режим, отступы под вырез и
тактильная отдача в браузере тоже не воспроизводятся — а именно они
отличают Mini App от страницы.

Нужен **отдельный бот для разработки**. Клиентский не годится: подпись
проверяется токеном того бота, который приложение запустил, и с чужим
первый же запрос ответит отказом.

```sh
# 1. BotFather → /newbot, токен нового бота — в TELEGRAM_BOT_TOKEN
# 2. Туннель до локального сервера: Telegram открывает только https
cloudflared tunnel --url http://localhost:3000
# 3. Полученный адрес — в MINIAPP_URL и в кнопку меню бота
curl -X POST "https://api.telegram.org/bot<токен>/setChatMenuButton" \
  -H 'content-type: application/json' \
  -d '{"menu_button":{"type":"web_app","text":"Обмен",
       "web_app":{"url":"https://<адрес туннеля>"}}}'
```

Вебхук при этом не трогается: сообщения бота для проверки вёрстки не
нужны, а `pnpm set-telegram-webhook` сам не запускается.

Три вещи, которые сбивают с толку:

- **Горячая замена через туннель не работает без разрешения.** Домен
  туннеля для dev-сервера чужой, и он молча отказывает в служебных
  запросах: страница открывается, а правки не доезжают. Разрешение —
  `allowedDevOrigins` в `apps/miniapp/next.config.ts`.
- **Telegram кэширует Mini App.** Правка не видна — Настройки → Данные и
  память → Очистить кэш.
- **Адрес бесплатного туннеля меняется при каждом запуске**, и менять
  его надо в двух местах: в `MINIAPP_URL` и в кнопке меню.

Если `cloudflared` не находит серверы Cloudflare и падает на
`lookup ... on [::1]:53`, дело в пустом `/etc/resolv.conf` — Go-программы
читают именно его, а macOS держит DNS в другом месте. Лечится либо
явными адресами (`sudo networksetup -setdnsservers Wi-Fi 1.1.1.1`), либо
запуском туннеля контейнером, у которого свой резолвер:

```sh
docker run --rm -d --name nemo-tunnel cloudflare/cloudflared:latest \
  tunnel --url http://host.docker.internal:3000
docker logs nemo-tunnel        # адрес печатается сюда
```

## Первый вход в админку

Второй фактор сотруднику выдаёт администратор, а первого администратора
выдать некому: пока список сотрудников пуст, войти нельзя вовсе.
Развернувший сервис заводит его скриптом:

```sh
pnpm create-first-admin <telegram_user_id> "Имя"
```

Скрипт печатает ключ для приложения-аутентификатора — второй раз он
показан не будет. На непустом списке сотрудников он отказывает: дальше
сотрудников заводит администратор в настройках, подраздел
«Сотрудники», там же выдаётся и сбрасывается второй фактор.

Заводит ключ администратор, но передавать его из рук в руки не
обязательно: пока ключом ни разу не входили, сотрудник увидит тот же код
для камеры на своём первом входе — после кнопки Telegram и перед полем
для кода. Первый сошедшийся код закрывает этот показ навсегда.

Ключ, который сотрудник заводил бы себе сам, достался бы тому, кто угнал
его аккаунт раньше, — поэтому вход ключей не создаёт, а только
показывает уже заведённый и ещё не сработавший.

### Вход на своей машине

Оба фактора на `localhost` недоступны: виджет Telegram Login требует
настоящий домен, привязанный к боту, и отвечает «Bot domain invalid», а
без него не начинается и шаг с кодом. Панель локально не открывалась бы
вовсе.

Поэтому в разработке под виджетом появляется вход по Telegram ID: два
фактора он пропускает, проверку сотрудника — нет. Войти можно только
тем, кто заведён, действует и кому выдан ключ, — той же операцией
`beginStaffLogin`, которой пользуется настоящий вход.

Включается он переменной, и одной её мало — нужна ещё сборка для
разработки:

```sh
ADMIN_DEV_LOGIN=1 pnpm --filter @nemo/admin dev
```

Проверяются оба условия и на экране, и в маршруте: показанная кнопка
решает, видно ли вход, а пускает маршрут — адрес набирается руками и без
кнопки. На сервере переменную не заводить: там она не сработает всё
равно, но её присутствие в окружении прода вводит в заблуждение.

### Если второй фактор потерян

Сотруднику его выдаёт заново администратор — в настройках, подраздел
«Сотрудники», рядом с именем; новый ключ сотрудник снова увидит на своём входе. Администратор
себе выдать не может: чтобы нажать кнопку, надо войти. Когда
администратор в сервисе один и потерял ключ он, помогает только консоль
сервера:

```sh
pnpm reissue-second-factor <telegram_user_id>
```

Запускать её нужно там, где есть `DATABASE_URL` и
`REQUISITES_PUBLIC_KEY` — то есть в контейнере админ-панели, а не на
машине разработчика: локальные переменные указывают на базу разработки,
и ключ обновится в ней.

Кроме кода для камеры скрипт печатает код, действующий в эту секунду. Он
отвечает на вопрос, из-за чего «код не подошёл»: если снятый камерой
ключ даёт в приложении другие цифры, разошлись часы телефона, а не ключ.

## Тесты

```sh
pnpm test
```

Тесты прикладных операций идут против настоящей базы: существенная часть
правил сервиса выражена ограничениями Postgres — обязательность дохода
при исполнении заявки, уникальность реферального начисления, запрет
самореферала, — и мок репозитория их не проверит. Схема тестовой базы
приводится в порядок автоматически перед прогоном, данные вычищаются
между тестами.

База у каждого пакета своя — `nemo_test_core`, `nemo_test_db` — и
создаётся сама при первом прогоне. Турбо запускает пакеты параллельно, и
на общей базе тесты вычищали бы данные друг у друга: падения выглядели бы
ошибками в коде, хотя код ни при чём.

Базовое имя переопределяется переменной `TEST_DATABASE_URL`; суффикс
пакета добавляется к нему.

## Развёртывание

Все три приложения — `miniapp`, `admin`, `cabinet` — собираются из своих
образов в `docker/`; контекст сборки — корень монорепо, потому что они
зависят от пакетов рабочего пространства. Образ несёт монорепо целиком,
а не самодостаточную сборку Next: драйвер базы объявлен внешним
пакетом и в `output: 'standalone'` не попадает — приложение падало бы
на первом обращении к базе.

Миграции применяет админ-панель при запуске: владелец схемы должен быть
один, иначе приложения станут накатывать её одновременно. Пока
экземпляр один, этого достаточно; при нескольких понадобится отдельный
шаг развёртывания — миграции не берут блокировку.

Порядок при первом развёртывании:

1. Поднять базу и задать `DATABASE_URL` всем трём приложениям.
2. `pnpm generate-keys` — публичный ключ (`REQUISITES_PUBLIC_KEY`) в
   клиентское приложение и в кабинет мерчанта, приватный **только** в
   админ-панель ([ADR-0002](docs/adr/0002-shifrovanie-rekvizitov-klienta.md)).
3. Задать в клиентском приложении: `TELEGRAM_BOT_TOKEN`,
   `TELEGRAM_WEBHOOK_SECRET`, `MINIAPP_URL` — и `ADMIN_URL`: по нему
   оно стучится в панель сразу после новой заявки или обращения, и
   менеджер узнаёт о поводе через секунду, а не следующим прогоном
   планировщика. До 4 сентября 2026 на проде эта переменная не была
   задана, и уведомления шли с задержкой до пяти минут. Сюда же —
   переменные почты из шага 5 (`EMAIL_DELIVERY`, `EMAIL_API_KEY`,
   `EMAIL_FROM`, `CABINET_URL`): письма мерчанту о сроке оплаты —
   полчаса до конца и отмена по сроку — шлёт планировщик этого
   приложения, потому что срок считает он.
4. Задать в админ-панели: тот же `TELEGRAM_BOT_TOKEN` (уведомления
   уходят от бота, которого клиент запускал), `ADMIN_LOGIN_BOT_TOKEN`,
   `ADMIN_BOT_WEBHOOK_SECRET`, `ADMIN_URL`, `ADMIN_SESSION_SECRET` — и
   те же переменные почты: решение по анкете и переходы заявки — курс
   подтверждён, оплата получена, исполнена, отменена менеджером —
   мерчанту пишет панель. Пишущих мерчанту процессов три, и переменные
   почты нужны каждому; без них письмо не уходит, а в журнал контейнера
   ложится «Письмо не отправлено … почта не настроена». 7 сентября 2026
   на dev переменные были только у кабинета.
5. Задать в кабинете мерчанта: `CABINET_URL` — его же адрес, он в
   каждом письме, и без него почта выключена в любом режиме;
   `CABINET_SESSION_SECRET` не короче 32 знаков; `API_KEY_PREFIX`
   (`sk_live_` на боевом, `sk_test_` на песочнице); `ADMIN_URL` и тот
   же `SCHEDULER_SECRET`, что у соседей: им кабинет толкает панель
   разослать сотрудникам новую заявку, и им же планировщик зовёт чистку
   журнала вызовов (шаг 10). Почта — одна и та же четвёрка у всех трёх
   приложений: `EMAIL_DELIVERY=provider` с
   `EMAIL_API_KEY` и `EMAIL_FROM` (Resend, домен подтверждён записями
   из раздела «Почта мерчантам» ниже) либо `EMAIL_DELIVERY=log` на
   контуре без своего домена: письмо целиком пишется в журнал
   контейнера, и ссылку подтверждения тестирующий берёт оттуда.
   Незаданная переменная — выключенная почта: регистрация отвечает об
   этом словами, а `GET /api/health` называет режим. Для входа
   амбассадоров — `TELEGRAM_BOT_USERNAME` (имя клиентского бота, без
   собачки) и его же `TELEGRAM_BOT_TOKEN`: первым витрина собирает
   кнопку Telegram и реферальную ссылку, вторым проверяет подпись
   входа. Без любой из них кнопки на витрине нет, и страница говорит
   об этом словами — молчащая кнопка хуже отсутствующей; вход мерчанта
   при этом работает. Имя здесь обычной переменной, а не
   `NEXT_PUBLIC_*`: страницы кабинета серверные, и вшитое на сборке имя
   менялось бы пересборкой. По желанию —
   `CABINET_SANDBOX_URL` (адрес песочницы для раздела «Песочница») и
   `RAPIRA_KEY`, как у клиентского приложения. POS-терминал:
   `POS_ACQUIRER` — кто принимает платежи; пока известна одна
   `imitation`, она же по умолчанию, а незнакомое имя не подменяется
   имитацией молча: терминал называет причину на экране, счёт не
   создаётся. `POS_DEMO_SEED=1`
   заводит мерчанту без счетов набор примерных счетов и возвратов,
   подписанных словом «пример», — для показа на dev; на боевом контуре
   не задавать.
6. `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` задать **аргументом сборки**, а
   не только переменной окружения: `NEXT_PUBLIC_*` Next подставляет в
   клиентский код на сборке, и переданное контейнеру в браузер уже не
   попадёт. У приложений здесь разные значения — клиентский бот и бот
   входа; у кабинета мерчанта аргументов сборки нет.
7. Развернуть, затем `pnpm set-telegram-webhook`,
   `pnpm set-telegram-webhook --admin` и `pnpm create-first-admin`.
8. У BotFather: `/setdomain` **боту входа** на домен админки — иначе
   виджет Telegram Login откажется работать, — Mini App клиентскому
   боту на `MINIAPP_URL` и `/setdomain` **клиентскому боту** на домен
   кабинета: его виджетом входят амбассадоры. Один бот держит один
   домен, и потому доменов здесь два бота: клиентский занят кабинетом,
   бот входа — админкой.
9. Наполнить справочники: `pnpm seed-directories` — USDT и рубль в обе
   стороны, безналично и наличными; доллар, евро, юань, лира, бат, рупия
   и рэнд только на выдачу и только безналично; плюс сети перевода TRC20,
   TON и BEP20. Скрипт приводит справочники к этому виду целиком: лишние
   валюты и направления удаляет, лишние сети гасит — на них ссылаются
   прошлые заявки и сохранённые клиентами реквизиты. Погашенное из
   панели направление он не трогает: это решение администратора,
   принятое по живой цене.
10. Настроить планировщик на два вызова раз в несколько минут — оба с
    заголовком `authorization: Bearer <SCHEDULER_SECRET>`:
    `POST /api/exchange-requests/deadlines` у клиентского приложения
    (предупреждает о подходящем сроке оплаты и отменяет неоплаченные
    заявки — без него обещанный курс держится бессрочно) и
    `POST /api/conversations/notify` у админки (рассылает сотрудникам
    новые обращения от бота входа — без него о вопросе клиента узнают,
    только открыв панель).

    Своего планировщика в проекте нет: приложения живут на serverless, где
    фоновому процессу негде работать, а расписание всё равно настраивается
    там же, где деплой. На Dokploy это раздел Schedules у приложения:
    `*/5 * * * *` и команда, дёргающая свой же адрес из переменных
    окружения —

    ```sh
    node -e "fetch(process.env.MINIAPP_URL + '/api/exchange-requests/deadlines', \
     { method: 'POST', headers: { authorization: 'Bearer ' + process.env.SCHEDULER_SECRET } }) \
     .then(async (r) => { console.log(r.status, await r.text()); if (!r.ok) process.exit(1); })"
    ```

    У админки то же самое с `ADMIN_URL` и `/api/conversations/notify`;
    у кабинета мерчанта — `CABINET_URL` и `/api/maintenance/purge-logs`,
    раз в сутки: журнал вызовов API хранится тридцать дней.
    Выход не нулём делает неудачный вызов видимым в списке запусков —
    иначе молчащий планировщик неотличим от работающего.
11. Задать экономику в настройках, подраздел «Экономика»: наценку, минимальную сумму
    обмена и срок жизни неоплаченной заявки. Значения из миграции —
    заглушки (2%, 35 USDT, 120 минут), и оставлять их нельзя: минимум
    подбирается по реальным комиссиям сети, которые сервис платит за
    клиента, — ориентир — покрывать комиссию не менее чем вдвое. Минимум
    задаётся в USDT: эту валюту клиент отдаёт или получает в каждом
    направлении, и в ней порог накрывает справочник целиком. Там же, в
    подразделе «Мерчанты», — ник Telegram поддержки мерчантов: на него
    зовут письма и кабинет, и без него ссылки «Поддержка» в них нет.
12. Завести ставки по ступеням: `pnpm seed-fee-schedules` ставит сетки
    на бат и юань. Юань — как в письме владельца; у бата их три, по
    способу выдачи: банк «4,5 % + 10 $» на нижней ступени, кошелёк и
    наличные «5,5 % + 10 $», дальше доля без фикса. Фикс один на все
    три — решение владельца от 9 сентября 2026 («пока по 10, везде»); в
    его письмах он был 5 $ на банк и 10 $ на остальное. Доля на нижней
    ступени идёт вместе с фиксом, а не вместо него: с одним фиксом
    меньшая сумма выходила дешевле большей, а такую сетку с 8 сентября
    2026 сервис не принимает (docs/adr/0019). Скрипт проверяет свои
    сетки тем же правилом, что и панель, до первой записи. Нужен он один раз — он
    пропускает валюту, у которой сетка уже заведена, и дальше ставки
    правит администратор в настройках, подраздел «Направления и
    комиссии». Где сетки нет, направление
    считается по наценке из предыдущего шага, и это рабочее состояние, а
    не пропуск: у обмена USDT на рубли своя экономика, ступени бата туда
    не переносятся.

Скрипты (`seed-directories`, `set-telegram-webhook`) запускаются с теми же
переменными, что и приложения; на Dokploy это тот же раздел Schedules —
выключенная задача с командой и кнопкой «выполнить». Если база наружу не
открыта, запускать их нужно изнутри контейнера админ-панели —
там уже есть и переменные, и доступ к базе.

### Почта мерчантам: домен и DNS

Письма мерчанту — подтверждение адреса, сброс пароля, решение по
анкете, переходы заявки — шлёт Resend
([ADR-0017](docs/adr/0017-merchant-vtoroy-vladelec-zayavki.md)) одним
HTTPS-запросом. Бесплатного тарифа хватает с запасом: три тысячи писем
в месяц и сто в сутки, а писем у кабинета — по нескольку на мерчанта.
Упирается всё в домен: на чужие ящики Resend отправляет только с
адреса на домене, который подтверждён записями в DNS, — поэтому до
покупки домена кабинет живёт на `sslip.io` и только на тестовом контуре
с `EMAIL_DELIVERY=log`.

Когда домен куплен, порядок такой:

1. В Resend добавить домен отправителя: сам домен — для
   `noreply@<домен>` боевого кабинета; для песочницы отдельный,
   `sandbox.<домен>` с `noreply@sandbox.<домен>`, если тариф вмещает
   второй (число доменов названо на странице тарифов Resend), иначе
   песочница остаётся в режиме `log`, и ссылки подтверждения на ней
   по-прежнему берут из журнала.
2. Прописать в DNS записи, которые Resend показывает у домена, —
   значения свои у каждого домена, вид один:
   - SPF: `MX send.<домен> → feedback-smtp.<регион>.amazonses.com`,
     приоритет 10, и `TXT send.<домен> = "v=spf1 include:amazonses.com
     ~all"` — с поддомена `send` уходят обратные адреса;
   - DKIM — в той форме, которую Resend показывает у домена: либо одна
     `TXT resend._domainkey.<домен>` с ключом, либо три
     `CNAME <id>._domainkey → <id>.dkim.amazonses.com`; CNAME-записи не
     прятать за прокси DNS-провайдера, иначе проверка не проходит;
   - DMARC: `TXT _dmarc.<домен> = "v=DMARC1; p=none;"` — Resend её не
     требует; запись про отчёты, а не про отказ, и писем она не режет;
   - запись `links.<домен>` для отслеживания переходов не нужна:
     ссылки в письмах ведут в кабинет, и переписывать их незачем.
3. Дождаться в Resend статуса «verified» — обычно четверть часа, DNS
   бывает тянет до трёх суток — и выпустить ключ API с правом только на
   отправку.
4. В переменные кабинета: `EMAIL_DELIVERY=provider`, `EMAIL_API_KEY`,
   `EMAIL_FROM=Tobee <noreply@<домен>>` — адрес на подтверждённом
   домене, иначе Resend отвечает отказом и письмо не уходит; и
   `CABINET_URL` на купленный домен, потому что он в каждом письме.
5. `GET /api/health` у кабинета называет режим почты; зарегистрировать
   мерчанта на боевом кабинете и получить письмо — это и есть проверка.

### Два контура

Контуров два, и различаются они веткой и ботом, а не кодом:

| | `production` | `dev` |
|---|---|---|
| ветка | `main` | `dev` |
| клиентский бот | `@NemoServiceBTC_bot` | `@devnemobot_bot` |
| кабинет мерчанта | боевой, ключи `sk_live_` | песочница, ключи `sk_test_` |
| база, ключи, секреты | свои | свои, ни один не общий с боевым |

Для мерчанта `dev` и есть песочница: тот же кабинет и то же API на
своём адресе, своя регистрация, свои ключи; анкету там одобряют из
тестовой панели, заявки двигает тот, кто её открыл. Отдельных тестовых
ключей внутри боевого контура нет — записано в `backlog.md`.

Оба живут на одном Dokploy окружениями одного проекта `nemo` — так их
невозможно перепутать: единственное окружение в панели однажды приняли
за тестовое. Ничего из `dev` не смотрит в боевую базу и не пишет
клиентам боевого бота: у контура свой Postgres, своя пара ключей
реквизитов, свои секреты вебхуков и планировщика.

Путь изменения один: ветка от `dev` → PR в `dev` → сам выезжает на
тестовый контур → проверяется руками через `@devnemobot_bot` →
`pnpm release` → боевой. Пока GitHub закрыт, вместо PR — проверки у
себя и push в `dev` зеркала; об этом ниже, «Выкат без GitHub». Релиз — это fast-forward: `main` становится
тем же самым коммитом, что стоит на `dev`, и на прод едет ровно то, что
смотрели, а не «то же плюс коммит слияния». В `main` не коммитят и PR
туда не открывают — он только догоняет `dev`, и git откажет, если
`main` вдруг ушёл вперёд. Обе ветки защищены, и правило действует и
на администраторов: обязательная проверка CI по коммиту, без
force-push. Различие одно: в `dev` изменения принимаются только через
PR, а в `main` требования PR нет — иначе fast-forward отклонялся бы;
проверка считается по коммиту, и у коммита с `dev` она уже есть. Тестовый контур — то место, где смотрят
глазами то, чего не видит ни один прогон: экран, кнопку, ответ бота.

После выката — `GET /api/health` у всех трёх приложений: `ok`, имя
приложения, коммит сборки и пульс базы. Маршрут открыт без подписи —
по нему же может стучать внешний сторожок раз в минуту — и потому не
говорит ничего сверх этого. Источников курса он не проверяет, а они
умеют молчать при зелёном пульсе: 27 августа 2026 евро и доллар девять
часов стояли без курса при живом `health`. Поэтому после выката ещё и
открыть Mini App и посмотреть пару через стакан — `RUB → EUR`: курс на
черте есть, в журнале контейнера нет строк «не ответила» и «брошен».

У `dev` один бот на всё: клиентский и бот входа в админку — это он же.
Код это допускает — `ADMIN_LOGIN_BOT_TOKEN` не задан, и вход
подписывает клиентский бот, — а виджет Telegram Login привязан к домену
командой `/setdomain` у BotFather на домен тестовой админки. Разделять
боты здесь незачем: ADR-0005 бережёт первый фактор боевого контура, а на
тестовом за ним ничего нет.

Отсюда следствие для входа амбассадора: **на `dev` он виджетом не
проверяется**. Один бот держит один домен, и домен у тестового занят
админкой; переключить его на кабинет значит закрыть вход в саму
админку. Проверяется там всё остальное — заведение амбассадора, отметка,
разделы кабинета, — а сама кнопка Telegram отвечает «Bot domain
invalid», и это ожидаемо. Живьём вход смотрится на боевом контуре, где
боты разделены: там клиентский бот свободен от виджета (Mini App
опознаёт клиента подписью запуска, а не им), и `/setdomain` ему ставится
на домен кабинета. Понадобится проверять вход и на тестовом — заводить
третьего бота под тестовый кабинет.

Ключа DeepSeek у `dev` нет, и консьерж там молчит — отвечает человек.
Это рабочий выключатель, а не поломка; проверять голос консьержа на
тестовом контуре — задать ключ в переменных окружения `miniapp`. Тот же
ключ у `admin` включает разбор документов в базу знаний; без него
панель говорит, что разбор выключен, и статьи пишутся руками.

### Выкат без GitHub

Обычный путь изменения идёт через GitHub: push → вебхук → Dokploy
собирает. Этот путь целиком зависит от чужого аккаунта, и 11 сентября
2026 он оборвался — GitHub заблокировал аккаунт, и репозиторий стал
недоступен даже приложению Dokploy. Уже выкаченное при этом работало:
контейнеры подняты, база своя. Встала только следующая выкатка.

Поэтому рядом стоит запасной источник — **зеркало репозитория на том же
сервере**: `/etc/dokploy/git/nemoProject.git`. Это обычный bare-репо, то
есть история без рабочих файлов. Каталог `/etc/dokploy` смонтирован в
контейнер Dokploy, поэтому зеркало для него — соседняя папка, а не сеть.
С 12 сентября 2026 из него собираются все шесть приложений обоих
контуров.

```sh
git remote add server ssh://root@<сервер>/etc/dokploy/git/nemoProject.git
git push server dev     # ветки те же: dev — тестовый контур, main — боевой
```

Отдаёт репозиторий отдельный пользователь `git` с оболочкой
`git-shell`: войти им нельзя, он умеет только принять и отдать
репозиторий. У Dokploy для него свой ключ.

В приложении источник переключается на **Git** с адресом
`git@172.18.0.1:/etc/dokploy/git/nemoProject.git` и той же веткой. Адрес
именно такой, и это не опечатка: сборка идёт из контейнера Dokploy, а он
живёт в своей сети — `172.17.0.1` (docker0) для него закрыт. Локальный
путь и `file://` Dokploy не принимает вовсе: требует формат SSH и ключ.

**Push в зеркало пересобирает контур сам**: `dev` — тестовый, `main` —
боевой. Делает это хук `post-receive`
([`scripts/mirror-post-receive.sh`](scripts/mirror-post-receive.sh), на
сервере — `hooks/post-receive` зеркала): он ставит в очередь Dokploy
приложения, у которых источник — это зеркало, ветка совпала с пушнутой
и включён автодеплой. Решает Dokploy, а не список в хуке, и приложение,
заведённое позже с тем же источником, подхватится само. Флаг
автодеплоя хук уважает, поэтому миграция, которую Mini App и кабинет
старой сборки не переживут, выкатывается как прежде: снять с них
автодеплой, push, дождаться новой панели — миграции накатывает она при
старте, — собрать их руками и вернуть флаг. Панель встаёт в очередь
первой и без этого, но это порядок сборки, а не гарантия, что миграция
успела.

Push хук не отменяет: git зовёт его после записи веток. Что ушло в
очередь, а что нет, печатается в выводе `git push` строками
`remote: автодеплой: …` и пишется в `/var/log/nemo-mirror-deploy.log`.
Отказ Dokploy виден там же — ветка при этом уже записана, и контур
стоит на прежнем коммите, пока сборку не запустят руками.

```sh
pnpm release                             # fast-forward main до dev в зеркале → боевой
git push -o no-deploy server dev         # записать ветку, ничего не собирая
# на сервере, из каталога зеркала: что собрал бы хук, не собирая
echo "<old> <new> refs/heads/dev" | DRY_RUN=1 hooks/post-receive
```

Ставится хук копированием файла в `hooks/post-receive` (владелец root,
права 755) и `git config receive.advertisePushOptions true` в зеркале —
без неё git отклоняет `-o`. Ключ Dokploy хук берёт из
`/root/.dokploy-key`: push идёт от root.

Чего этот путь не даёт: pull request'ов, ревью и GitHub Actions. Значит
проверки из `.github/workflows/ci.yml` — типы, тесты и сборка на чистой
машине с Postgres — здесь не запускаются, и прогонять их надо у себя до
push в `dev`, а раз push теперь сразу и выкат — тем более:

```sh
pnpm typecheck --force && pnpm exec turbo test --force && pnpm build --force
```

`--force` не лишний: без него turbo отдаёт из кэша прогон того же
коммита, сделанный в соседнем worktree, и зелёный цвет оказывается
чужим и старым. А `pnpm test --force` не сработает вовсе — `test`
встроенная команда pnpm, и флаг достаётся ей, а не turbo.

Зеркало стоит держать и после того, как GitHub вернётся: push в оба
адреса дешевле, чем однажды снова остаться без единственной копии.

## Проверки на PR

`.github/workflows/ci.yml` прогоняет на каждом PR то же, что и локально:
типы, миграции на чистой базе, тесты против настоящего Postgres той же
версии, что в `docker-compose.yml`, и сборку приложений.

Ревью кода делает CodeRabbit, и сам он не приходит: на бесплатном тарифе
для открытых репозиториев репозиторий меньше чем с десятью звёздами
ревьюится только по команде. Когда PR готов, в нём пишут
`@coderabbitai review` и сливают после того, как ревью пришло, а
замечания разобраны. Ревью одно в час на автора PR, поэтому просят его
один раз на готовый PR, а не на каждую правку; после правок — той же
командой. Ответ бота «Review skipped» или «Review limit reached» — это не
«замечаний нет», а «ревью не было»: проверка CodeRabbit при этом
зелёная, и строгий CI такое слияние не остановит. Настройка — в
`.coderabbit.yaml`, почему выбран он, а не Greptile, — в
`.scratch/review-bots/`.

Сервис развёрнут **временно** на Dokploy: постоянное место зависит от
юрисдикции — того же вопроса, из-за которого не выбран хостинг базы
(блокер A1). Приложения пересобираются по push: `dev` — на тестовый
контур, `main` — на боевой; домены временные, на `sslip.io`, и меняются
вместе с переездом. После смены домена нужно перерегистрировать вебхуки
и повторить `/setdomain`.

## Устройство

- `apps/miniapp` — Telegram Mini App и вебхук бота на grammY.
- `apps/admin` — админ-панель для менеджеров, отдельный деплой.
- `apps/cabinet` — кабинет мерчанта: сайт с почтой и паролем, где
  бизнес заводит анкету и следит за своими заявками (порт 3002 в
  разработке). Входят в него люди мерчанта, и ролей у них три —
  владелец, оператор, наблюдатель
  ([ADR-0023](docs/adr/0023-lyudi-merchanta-vhodyat-a-ne-organizaciya.md));
  сотрудников заводит владелец в разделе «Сотрудники», пароль передаёт
  лично, а закрытый доступ обрывает вход в ту же секунду. Там же живёт API мерчанта `/api/v1` — ключи
  `Authorization: Bearer sk_…`, договор в `docs/api/merchant-v1.yaml`,
  и тест сверяет его с маршрутами. Ключам нужен `API_KEY_PREFIX`
  (`sk_live_` на боевом, `sk_test_` на песочнице), толчку панели о
  новой заявке — `ADMIN_URL` и `SCHEDULER_SECRET`, разделу «Песочница»
  — `CABINET_SANDBOX_URL`; журнал вызовов и отжившие сессии кабинета
  чистит планировщик раз в сутки: `POST /api/maintenance/purge-logs`
  с тем же секретом.
  Вебхуки мерчантов разбирает воркер, живущий в процессе кабинета
  ([ADR-0018](docs/adr/0018-vebhuki-cherez-ishodyaschuyu-ochered-v-baze.md)):
  планировщика ему не нужно, но доставки идут, только пока кабинет
  поднят. POS-терминал, счета и возвраты — макет без денег: приём
  платежа стоит за швом провайдера с единственной реализацией,
  имитацией
  ([ADR-0024](docs/adr/0024-priyom-platezha-za-shvom-provaydera.md)),
  и банк встанет за тот же интерфейс. Что кабинет умеет и как
  устроен, одним документом для показа заказчику —
  [docs/merchant-cabinet.md](docs/merchant-cabinet.md).
- `packages/core` — прикладные операции: единственное место, где
  меняется состояние системы.
- `packages/http` — общая обвязка маршрутов всех приложений: как
  отказы операций превращаются в коды HTTP и как отдаётся JSON, в
  котором есть bigint и денежные строки.
- `packages/telegram` — доставка уведомлений: переходы заявки на обмен
  отправляет админка, регистрацию реферала — Mini App, и клиент должен
  получать их одинаково.
- `packages/email` — то же для мерчанта: у бизнеса нет Telegram, и
  письма ему шлёт этот пакет. Режим доставки объявляется явно
  (`EMAIL_DELIVERY`): `provider` — настоящая отправка, `log` — письмо
  целиком в журнал контейнера (так ссылку подтверждения забирают на
  контуре без своего домена), не задано — почта выключена, и
  регистрация со сбросом пароля отвечают об этом словами.
- `packages/ui` — детали рабочих интерфейсов и оформление к ним: их
  делят панель менеджера и кабинет мерчанта.
- `packages/db` — схема и доступ к Postgres через Drizzle.
- `packages/types` — доменные типы и денежная арифметика.
- `packages/crypto` — асимметричное шифрование реквизитов.
- `packages/qr` — чтение QR из картинки в браузере: его делят Mini App
  и кабинет мерчанта, фикстуры и генератор картинок лежат рядом.
- `packages/rates` — источники курса: биржи Rapira и Bitkub,
  P2P-раздел HTX, опорные курсы ЕЦБ — реализации интерфейса из
  `@nemo/core`, цепочка из них и составной источник поверх цепочки.
  Отдельным пакетом, потому что провайдеров несколько, а заявка на
  обмен не должна знать, у кого именно спрошена цена
  ([ADR-0007](docs/adr/0007-vtoroy-istochnik-kursa-fiat-cherez-dollar.md));
  снимки держатся тёплыми обновлением по таймеру
  ([ADR-0010](docs/adr/0010-kurs-derzhitsya-tyoplym.md)).

Приложений три, а не одно: приватный ключ расшифровки реквизитов
физически отсутствует в клиентском деплое ([ADR-0002](docs/adr/0002-shifrovanie-rekvizitov-klienta.md)),
и кабинет мерчанта стоит в том же клиентском контуре — реквизиты он
шифрует, а показывает их менеджер из панели.

## Миграции

```sh
pnpm db:generate          # сгенерировать миграцию по изменениям в схеме
pnpm db:migrate           # применить к базе разработки
pnpm db:studio            # посмотреть данные
```

Схема живёт в `packages/db/src/schema.ts`, миграции — в
`packages/db/migrations`. Правится схема, миграция генерируется по ней;
писать миграцию руками означает разойтись со схемой. Сгенерированной
миграции стоит дать говорящее имя вместо случайного — и в файле, и в
`meta/_journal.json`.

## Скрипты

```sh
pnpm generate-keys            # пара ключей шифрования реквизитов
pnpm create-first-admin       # первый администратор, на пустом списке
pnpm set-telegram-webhook     # регистрация вебхука, см. раздел о ботах
pnpm seed-directories         # справочники: девять валют, направления и сети
pnpm seed-fee-schedules       # ставки по ступеням для бата и юаня
```

Все читают переменные из `.env`, если он есть, и из окружения.
