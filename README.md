# nemoProject

Сервис обмена валют через Telegram: клиент подаёт заявку в Mini App,
менеджер исполняет её вручную через админ-панель. Доменный язык — в
[CONTEXT.md](CONTEXT.md), принятые решения — в [docs/adr](docs/adr).

## Запуск

Нужны Node 22+, pnpm 9 и Docker.

```sh
pnpm install
docker compose up -d      # Postgres на localhost:5432, базы nemo_dev и nemo_test
pnpm db:migrate           # применить миграции к базе разработки
cp .env.example .env      # заполнить токен бота
pnpm generate-keys        # выпустить пару ключей шифрования реквизитов в .env
pnpm dev
git config core.hooksPath .githooks   # напоминание про CHANGELOG.md при коммите
```

`docker compose up -d` создаёт обе базы: `nemo_dev` для разработки и
`nemo_test` для тестов. Данные лежат в томе `nemo-pgdata` и переживают
перезапуск контейнера; `docker compose down -v` стирает их вместе с ним.

Postgres поднимается в контейнере, а не устанавливается в систему,
потому что версия базы — часть окружения проекта, и она должна
совпадать у всех, кто с ним работает.

## Два бота и их вебхуки

Ботов два, и это решение, а не случайность
([ADR-0005](docs/adr/0005-otdelnyy-bot-dlya-vhoda-v-adminku.md)):

- **клиентский** — его запускают покупатели, через него уходят
  уведомления о заявках. Токен лежит в обоих деплоях: клиентскому нужно
  принимать обновления, админке — отправлять сообщения.
- **бот входа** — показывает кнопку Telegram Login на странице админки.
  Его токен есть только в деплое админки, поэтому утечка клиентского
  контура не даёт подделать первый фактор входа.

Обновления оба принимают вебхуком, а не опросом: приложения живут на
serverless, где некому держать длинный опрос между запросами
([ADR-0001](docs/adr/0001-mini-app-kak-osnovnoy-interfeys.md)).

```sh
pnpm set-telegram-webhook                  # клиентский бот, по MINIAPP_URL
pnpm set-telegram-webhook --admin          # бот входа, по ADMIN_URL
pnpm set-telegram-webhook --info           # что зарегистрировано сейчас
pnpm set-telegram-webhook --admin --info
pnpm set-telegram-webhook --delete         # снять
```

Бот входа отвечает на `/start` ссылкой на админку. Своей работы у него
там нет — но молчащий бот выглядит сломанным, и первым делом в нём
начинают искать саму админ-панель.

Регистрация передаёт `secret_token` — `TELEGRAM_WEBHOOK_SECRET` у
клиентского бота, `ADMIN_BOT_WEBHOOK_SECRET` у бота входа, — а маршрут
сверяет его с заголовком `x-telegram-bot-api-secret-token` и без
совпадения не отвечает: адрес вебхука рано или поздно утекает, и без
секрета кто угодно сможет присылать боту поддельные обновления. Секреты
разные: боты разные, и общий связал бы их обратно.

Команду нужно повторить после каждой смены домена — Telegram шлёт
обновления по тому адресу, который ему назвали последним.

## Первый вход в админку

Второй фактор сотруднику выдаёт администратор, а первого администратора
выдать некому: пока список сотрудников пуст, войти нельзя вовсе.
Развернувший сервис заводит его скриптом:

```sh
pnpm create-first-admin <telegram_user_id> "Имя"
```

Скрипт печатает ключ для приложения-аутентификатора — второй раз он
показан не будет. На непустом списке сотрудников он отказывает: дальше
сотрудников заводит администратор через раздел настроек, там же
выдаётся и сбрасывается второй фактор.

Секрет, который сотрудник заводил бы себе сам при первом входе, достался
бы тому, кто угнал его аккаунт раньше, — то есть не сработал бы ровно в
том случае, ради которого второй фактор и заведён.

### Если второй фактор потерян

Сотруднику его выдаёт заново администратор — в разделе настроек, рядом с
именем. Администратор себе выдать не может: чтобы нажать кнопку, надо
войти. Когда администратор в сервисе один и потерял ключ он, помогает
только консоль сервера:

```sh
pnpm reissue-second-factor <telegram_user_id>
```

Запускать её нужно там, где есть `DATABASE_URL` и
`REQUISITES_PUBLIC_KEY` — то есть в контейнере админ-панели, а не на
машине разработчика: локальные переменные указывают на базу разработки,
и ключ обновится в ней.

Кроме кода для камеры скрипт печатает код, действующий в эту секунду. Он
отвечает на вопрос, из-за чего «код не подошёл»: если снятый камерой
ключ даёт в приложении другие цифры, разошлись часы телефона, а не ключ.

## Тесты

```sh
pnpm test
```

Тесты прикладных операций идут против настоящей базы: существенная часть
правил сервиса выражена ограничениями Postgres — обязательность дохода
при исполнении заявки, уникальность реферального начисления, запрет
самореферала, — и мок репозитория их не проверит. Схема тестовой базы
приводится в порядок автоматически перед прогоном, данные вычищаются
между тестами.

База у каждого пакета своя — `nemo_test_core`, `nemo_test_db` — и
создаётся сама при первом прогоне. Турбо запускает пакеты параллельно, и
на общей базе тесты вычищали бы данные друг у друга: падения выглядели бы
ошибками в коде, хотя код ни при чём.

Базовое имя переопределяется переменной `TEST_DATABASE_URL`; суффикс
пакета добавляется к нему.

## Развёртывание

Оба приложения собираются из своих образов в `docker/`; контекст сборки —
корень монорепо, потому что они зависят от пакетов рабочего
пространства. Образ несёт монорепо целиком, а не самодостаточную сборку
Next: драйвер базы объявлен внешним пакетом и в `output: 'standalone'`
не попадает — приложение падало бы на первом обращении к базе.

Миграции применяет админ-панель при запуске: владелец схемы должен быть
один, иначе два приложения станут накатывать её одновременно. Пока
экземпляр один, этого достаточно; при нескольких понадобится отдельный
шаг развёртывания — миграции не берут блокировку.

Порядок при первом развёртывании:

1. Поднять базу и задать `DATABASE_URL` обоим приложениям.
2. `pnpm generate-keys` — публичный ключ в оба приложения, приватный
   **только** в админ-панель ([ADR-0002](docs/adr/0002-shifrovanie-rekvizitov-klienta.md)).
3. Задать в клиентском приложении: `TELEGRAM_BOT_TOKEN`,
   `TELEGRAM_WEBHOOK_SECRET`, `MINIAPP_URL`.
4. Задать в админ-панели: тот же `TELEGRAM_BOT_TOKEN` (уведомления
   уходят от бота, которого клиент запускал), `ADMIN_LOGIN_BOT_TOKEN`,
   `ADMIN_BOT_WEBHOOK_SECRET`, `ADMIN_URL`, `ADMIN_SESSION_SECRET`.
5. `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` задать **аргументом сборки**, а
   не только переменной окружения: `NEXT_PUBLIC_*` Next подставляет в
   клиентский код на сборке, и переданное контейнеру в браузер уже не
   попадёт. У приложений здесь разные значения — клиентский бот и бот
   входа.
6. Развернуть, затем `pnpm set-telegram-webhook`,
   `pnpm set-telegram-webhook --admin` и `pnpm create-first-admin`.
7. У BotFather: `/setdomain` **боту входа** на домен админки — иначе
   виджет Telegram Login откажется работать, — и Mini App клиентскому
   боту на `MINIAPP_URL`.
8. Наполнить справочники: `pnpm seed-directories` — USDT и рубль в обе
   стороны, безналично и наличными, плюс сети перевода TRC20 и TON.
   Скрипт приводит справочники к этому виду целиком: лишние валюты и
   направления удаляет, лишние сети гасит — на них ссылаются прошлые
   заявки и сохранённые клиентами реквизиты.
9. Настроить планировщик на два вызова раз в несколько минут — оба с
   заголовком `authorization: Bearer <SCHEDULER_SECRET>`:
   `POST /api/exchange-requests/deadlines` у клиентского приложения
   (предупреждает о подходящем сроке оплаты и отменяет неоплаченные
   заявки — без него обещанный курс держится бессрочно) и
   `POST /api/conversations/notify` у админки (рассылает сотрудникам
   новые обращения от бота входа — без него о вопросе клиента узнают,
   только открыв панель).
10. Задать экономику в разделе настроек: наценку, минимальную сумму
    обмена и срок жизни неоплаченной заявки. Значения из миграции —
    заглушки (2%, 3000 ₽, 120 минут), и оставлять их нельзя: минимум
    подбирается по реальным комиссиям сети, которые сервис платит за
    клиента, — ориентир — покрывать комиссию не менее чем вдвое.

Скрипты запускаются с теми же переменными, что и приложения. Если база
наружу не открыта, запускать их нужно изнутри контейнера админ-панели —
там уже есть и переменные, и доступ к базе.

## Проверки на PR

`.github/workflows/ci.yml` прогоняет на каждом PR то же, что и локально:
типы, миграции на чистой базе, тесты против настоящего Postgres той же
версии, что в `docker-compose.yml`, и сборку обоих приложений.

Сервис развёрнут **временно** на Dokploy: постоянное место зависит от
юрисдикции — того же вопроса, из-за которого не выбран хостинг базы
(блокер A1). Оба приложения пересобираются по push в `main`; домены
временные, на `sslip.io`, и меняются вместе с переездом. После смены
домена нужно перерегистрировать вебхуки и повторить `/setdomain`.

## Устройство

- `apps/miniapp` — Telegram Mini App и вебхук бота на grammY.
- `apps/admin` — админ-панель для менеджеров, отдельный деплой.
- `packages/core` — прикладные операции: единственное место, где
  меняется состояние системы.
- `packages/http` — общая обвязка маршрутов обоих приложений: как
  отказы операций превращаются в коды HTTP и как отдаётся JSON, в
  котором есть bigint и денежные строки.
- `packages/telegram` — доставка уведомлений: переходы заявки на обмен
  отправляет админка, регистрацию реферала — Mini App, и клиент должен
  получать их одинаково.
- `packages/db` — схема и доступ к Postgres через Drizzle.
- `packages/types` — доменные типы и денежная арифметика.
- `packages/crypto` — асимметричное шифрование реквизитов.
- `packages/rates` — котировки Rapira: реализация источника курса,
  интерфейс которого объявлен в `@nemo/core`. Отдельным пакетом, потому
  что провайдеров будет несколько, а заявка на обмен не должна знать,
  у кого именно спрошена цена.

Приложений два, а не одно: приватный ключ расшифровки реквизитов
физически отсутствует в клиентском деплое ([ADR-0002](docs/adr/0002-shifrovanie-rekvizitov-klienta.md)).

## Миграции

```sh
pnpm db:generate          # сгенерировать миграцию по изменениям в схеме
pnpm db:migrate           # применить к базе разработки
pnpm db:studio            # посмотреть данные
```

Схема живёт в `packages/db/src/schema.ts`, миграции — в
`packages/db/migrations`. Правится схема, миграция генерируется по ней;
писать миграцию руками означает разойтись со схемой. Сгенерированной
миграции стоит дать говорящее имя вместо случайного — и в файле, и в
`meta/_journal.json`.

## Скрипты

```sh
pnpm generate-keys            # пара ключей шифрования реквизитов
pnpm create-first-admin       # первый администратор, на пустом списке
pnpm set-telegram-webhook     # регистрация вебхука, см. раздел о ботах
pnpm seed-directories         # справочники: пара USDT — рубль и сети перевода
```

Все читают переменные из `.env`, если он есть, и из окружения.
