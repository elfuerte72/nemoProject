# nemoProject

Сервис обмена валют через Telegram: клиент подаёт заявку в Mini App,
менеджер исполняет её вручную через админ-панель. Доменный язык — в
[CONTEXT.md](CONTEXT.md), принятые решения — в [docs/adr](docs/adr).

## Запуск

Нужны Node 22+, pnpm 9 и Docker.

```sh
pnpm install
docker compose up -d      # Postgres на localhost:5432, базы nemo_dev и nemo_test
pnpm db:migrate           # применить миграции к базе разработки
cp .env.example .env      # заполнить токен бота
pnpm generate-keys        # выпустить пару ключей шифрования реквизитов в .env
pnpm seed-directories     # завести валюты, направления и сети
ln -sfn ../../.env apps/miniapp/.env   # Next читает .env из папки приложения,
ln -sfn ../../.env apps/admin/.env     # а не из корня монорепо
pnpm dev
git config core.hooksPath .githooks   # напоминание про CHANGELOG.md при коммите
```

Ссылки на `.env` обязательны, и забыть их легко: корневой файл читают
скрипты, а приложения — нет, и `pnpm dev` поднимется, но первый же
запрос ответит «Не задан TELEGRAM_BOT_TOKEN». Ссылка, а не копия, чтобы
секреты не разошлись по трём местам; под `.gitignore` она попадает тем же
правилом, что и сам файл, — то есть в клон не приезжает и заводится
руками.

Без `pnpm seed-directories` приложение откроется, но экран обмена
скажет, что направления не заведены: справочники наполняются скриптом, а
не миграцией.

`docker compose up -d` создаёт обе базы: `nemo_dev` для разработки и
`nemo_test` для тестов. Данные лежат в томе `nemo-pgdata` и переживают
перезапуск контейнера; `docker compose down -v` стирает их вместе с ним.

Postgres поднимается в контейнере, а не устанавливается в систему,
потому что версия базы — часть окружения проекта, и она должна
совпадать у всех, кто с ним работает.

## Два бота и их вебхуки

Ботов два, и это решение, а не случайность
([ADR-0005](docs/adr/0005-otdelnyy-bot-dlya-vhoda-v-adminku.md)):

- **клиентский** — его запускают покупатели, через него уходят
  уведомления о заявках. Токен лежит в обоих деплоях: клиентскому нужно
  принимать обновления, админке — отправлять сообщения.
- **бот входа** — показывает кнопку Telegram Login на странице админки.
  Его токен есть только в деплое админки, поэтому утечка клиентского
  контура не даёт подделать первый фактор входа.

Обновления оба принимают вебхуком, а не опросом: приложения живут на
serverless, где некому держать длинный опрос между запросами
([ADR-0001](docs/adr/0001-mini-app-kak-osnovnoy-interfeys.md)).

```sh
pnpm set-telegram-webhook                  # клиентский бот, по MINIAPP_URL
pnpm set-telegram-webhook --admin          # бот входа, по ADMIN_URL
pnpm set-telegram-webhook --info           # что зарегистрировано сейчас
pnpm set-telegram-webhook --admin --info
pnpm set-telegram-webhook --delete         # снять
```

Бот входа отвечает адресом админки и порядком входа на любое сообщение
в личной переписке, а не только на `/start`. Своей работы у него там
нет — но молчащий бот выглядит сломанным, и первым делом в нём начинают
искать саму админ-панель. Сотрудник, у которого вход не выходит, пишет
боту словами, а команду угадывать не приходится: её не знают как раз
те, кому бот и нужен.

Регистрация передаёт `secret_token` — `TELEGRAM_WEBHOOK_SECRET` у
клиентского бота, `ADMIN_BOT_WEBHOOK_SECRET` у бота входа, — а маршрут
сверяет его с заголовком `x-telegram-bot-api-secret-token` и без
совпадения не отвечает: адрес вебхука рано или поздно утекает, и без
секрета кто угодно сможет присылать боту поддельные обновления. Секреты
разные: боты разные, и общий связал бы их обратно.

Команду нужно повторить после каждой смены домена — Telegram шлёт
обновления по тому адресу, который ему назвали последним.

## Как посмотреть Mini App с телефона

В браузере оно не открывается вовсе: подпись `initData` проверяется
всегда, и обхода в коде нет. Полноэкранный режим, отступы под вырез и
тактильная отдача в браузере тоже не воспроизводятся — а именно они
отличают Mini App от страницы.

Нужен **отдельный бот для разработки**. Клиентский не годится: подпись
проверяется токеном того бота, который приложение запустил, и с чужим
первый же запрос ответит отказом.

```sh
# 1. BotFather → /newbot, токен нового бота — в TELEGRAM_BOT_TOKEN
# 2. Туннель до локального сервера: Telegram открывает только https
cloudflared tunnel --url http://localhost:3000
# 3. Полученный адрес — в MINIAPP_URL и в кнопку меню бота
curl -X POST "https://api.telegram.org/bot<токен>/setChatMenuButton" \
  -H 'content-type: application/json' \
  -d '{"menu_button":{"type":"web_app","text":"Обмен",
       "web_app":{"url":"https://<адрес туннеля>"}}}'
```

Вебхук при этом не трогается: сообщения бота для проверки вёрстки не
нужны, а `pnpm set-telegram-webhook` сам не запускается.

Три вещи, которые сбивают с толку:

- **Горячая замена через туннель не работает без разрешения.** Домен
  туннеля для dev-сервера чужой, и он молча отказывает в служебных
  запросах: страница открывается, а правки не доезжают. Разрешение —
  `allowedDevOrigins` в `apps/miniapp/next.config.ts`.
- **Telegram кэширует Mini App.** Правка не видна — Настройки → Данные и
  память → Очистить кэш.
- **Адрес бесплатного туннеля меняется при каждом запуске**, и менять
  его надо в двух местах: в `MINIAPP_URL` и в кнопке меню.

Если `cloudflared` не находит серверы Cloudflare и падает на
`lookup ... on [::1]:53`, дело в пустом `/etc/resolv.conf` — Go-программы
читают именно его, а macOS держит DNS в другом месте. Лечится либо
явными адресами (`sudo networksetup -setdnsservers Wi-Fi 1.1.1.1`), либо
запуском туннеля контейнером, у которого свой резолвер:

```sh
docker run --rm -d --name nemo-tunnel cloudflare/cloudflared:latest \
  tunnel --url http://host.docker.internal:3000
docker logs nemo-tunnel        # адрес печатается сюда
```

## Первый вход в админку

Второй фактор сотруднику выдаёт администратор, а первого администратора
выдать некому: пока список сотрудников пуст, войти нельзя вовсе.
Развернувший сервис заводит его скриптом:

```sh
pnpm create-first-admin <telegram_user_id> "Имя"
```

Скрипт печатает ключ для приложения-аутентификатора — второй раз он
показан не будет. На непустом списке сотрудников он отказывает: дальше
сотрудников заводит администратор через раздел настроек, там же
выдаётся и сбрасывается второй фактор.

Заводит ключ администратор, но передавать его из рук в руки не
обязательно: пока ключом ни разу не входили, сотрудник увидит тот же код
для камеры на своём первом входе — после кнопки Telegram и перед полем
для кода. Первый сошедшийся код закрывает этот показ навсегда.

Ключ, который сотрудник заводил бы себе сам, достался бы тому, кто угнал
его аккаунт раньше, — поэтому вход ключей не создаёт, а только
показывает уже заведённый и ещё не сработавший.

### Вход на своей машине

Оба фактора на `localhost` недоступны: виджет Telegram Login требует
настоящий домен, привязанный к боту, и отвечает «Bot domain invalid», а
без него не начинается и шаг с кодом. Панель локально не открывалась бы
вовсе.

Поэтому в разработке под виджетом появляется вход по Telegram ID: два
фактора он пропускает, проверку сотрудника — нет. Войти можно только
тем, кто заведён, действует и кому выдан ключ, — той же операцией
`beginStaffLogin`, которой пользуется настоящий вход.

Включается он переменной, и одной её мало — нужна ещё сборка для
разработки:

```sh
ADMIN_DEV_LOGIN=1 pnpm --filter @nemo/admin dev
```

Проверяются оба условия и на экране, и в маршруте: показанная кнопка
решает, видно ли вход, а пускает маршрут — адрес набирается руками и без
кнопки. На сервере переменную не заводить: там она не сработает всё
равно, но её присутствие в окружении прода вводит в заблуждение.

### Если второй фактор потерян

Сотруднику его выдаёт заново администратор — в разделе настроек, рядом с
именем; новый ключ сотрудник снова увидит на своём входе. Администратор
себе выдать не может: чтобы нажать кнопку, надо войти. Когда
администратор в сервисе один и потерял ключ он, помогает только консоль
сервера:

```sh
pnpm reissue-second-factor <telegram_user_id>
```

Запускать её нужно там, где есть `DATABASE_URL` и
`REQUISITES_PUBLIC_KEY` — то есть в контейнере админ-панели, а не на
машине разработчика: локальные переменные указывают на базу разработки,
и ключ обновится в ней.

Кроме кода для камеры скрипт печатает код, действующий в эту секунду. Он
отвечает на вопрос, из-за чего «код не подошёл»: если снятый камерой
ключ даёт в приложении другие цифры, разошлись часы телефона, а не ключ.

## Тесты

```sh
pnpm test
```

Тесты прикладных операций идут против настоящей базы: существенная часть
правил сервиса выражена ограничениями Postgres — обязательность дохода
при исполнении заявки, уникальность реферального начисления, запрет
самореферала, — и мок репозитория их не проверит. Схема тестовой базы
приводится в порядок автоматически перед прогоном, данные вычищаются
между тестами.

База у каждого пакета своя — `nemo_test_core`, `nemo_test_db` — и
создаётся сама при первом прогоне. Турбо запускает пакеты параллельно, и
на общей базе тесты вычищали бы данные друг у друга: падения выглядели бы
ошибками в коде, хотя код ни при чём.

Базовое имя переопределяется переменной `TEST_DATABASE_URL`; суффикс
пакета добавляется к нему.

## Развёртывание

Оба приложения собираются из своих образов в `docker/`; контекст сборки —
корень монорепо, потому что они зависят от пакетов рабочего
пространства. Образ несёт монорепо целиком, а не самодостаточную сборку
Next: драйвер базы объявлен внешним пакетом и в `output: 'standalone'`
не попадает — приложение падало бы на первом обращении к базе.

Миграции применяет админ-панель при запуске: владелец схемы должен быть
один, иначе два приложения станут накатывать её одновременно. Пока
экземпляр один, этого достаточно; при нескольких понадобится отдельный
шаг развёртывания — миграции не берут блокировку.

Порядок при первом развёртывании:

1. Поднять базу и задать `DATABASE_URL` обоим приложениям.
2. `pnpm generate-keys` — публичный ключ в оба приложения, приватный
   **только** в админ-панель ([ADR-0002](docs/adr/0002-shifrovanie-rekvizitov-klienta.md)).
3. Задать в клиентском приложении: `TELEGRAM_BOT_TOKEN`,
   `TELEGRAM_WEBHOOK_SECRET`, `MINIAPP_URL`.
4. Задать в админ-панели: тот же `TELEGRAM_BOT_TOKEN` (уведомления
   уходят от бота, которого клиент запускал), `ADMIN_LOGIN_BOT_TOKEN`,
   `ADMIN_BOT_WEBHOOK_SECRET`, `ADMIN_URL`, `ADMIN_SESSION_SECRET`.
5. `NEXT_PUBLIC_TELEGRAM_BOT_USERNAME` задать **аргументом сборки**, а
   не только переменной окружения: `NEXT_PUBLIC_*` Next подставляет в
   клиентский код на сборке, и переданное контейнеру в браузер уже не
   попадёт. У приложений здесь разные значения — клиентский бот и бот
   входа.
6. Развернуть, затем `pnpm set-telegram-webhook`,
   `pnpm set-telegram-webhook --admin` и `pnpm create-first-admin`.
7. У BotFather: `/setdomain` **боту входа** на домен админки — иначе
   виджет Telegram Login откажется работать, — и Mini App клиентскому
   боту на `MINIAPP_URL`.
8. Наполнить справочники: `pnpm seed-directories` — USDT и рубль в обе
   стороны, безналично и наличными; доллар, евро, юань, лира, бат, рупия
   и рэнд только на выдачу и только безналично; плюс сети перевода TRC20
   и TON. Скрипт приводит справочники к этому виду целиком: лишние
   валюты и направления удаляет, лишние сети гасит — на них ссылаются
   прошлые заявки и сохранённые клиентами реквизиты. Погашенное из
   панели направление он не трогает: это решение администратора,
   принятое по живой цене.
9. Настроить планировщик на два вызова раз в несколько минут — оба с
   заголовком `authorization: Bearer <SCHEDULER_SECRET>`:
   `POST /api/exchange-requests/deadlines` у клиентского приложения
   (предупреждает о подходящем сроке оплаты и отменяет неоплаченные
   заявки — без него обещанный курс держится бессрочно) и
   `POST /api/conversations/notify` у админки (рассылает сотрудникам
   новые обращения от бота входа — без него о вопросе клиента узнают,
   только открыв панель).

   Своего планировщика в проекте нет: приложения живут на serverless, где
   фоновому процессу негде работать, а расписание всё равно настраивается
   там же, где деплой. На Dokploy это раздел Schedules у приложения:
   `*/5 * * * *` и команда, дёргающая свой же адрес из переменных
   окружения —

   ```sh
   node -e "fetch(process.env.MINIAPP_URL + '/api/exchange-requests/deadlines', \
     { method: 'POST', headers: { authorization: 'Bearer ' + process.env.SCHEDULER_SECRET } }) \
     .then(async (r) => { console.log(r.status, await r.text()); if (!r.ok) process.exit(1); })"
   ```

   У админки то же самое с `ADMIN_URL` и `/api/conversations/notify`.
   Выход не нулём делает неудачный вызов видимым в списке запусков —
   иначе молчащий планировщик неотличим от работающего.
10. Задать экономику в разделе настроек: наценку, минимальную сумму
    обмена и срок жизни неоплаченной заявки. Значения из миграции —
    заглушки (2%, 35 USDT, 120 минут), и оставлять их нельзя: минимум
    подбирается по реальным комиссиям сети, которые сервис платит за
    клиента, — ориентир — покрывать комиссию не менее чем вдвое. Минимум
    задаётся в USDT: эту валюту клиент отдаёт или получает в каждом
    направлении, и в ней порог накрывает справочник целиком.
11. Завести ставки по ступеням: `pnpm seed-fee-schedules` ставит сетки,
    которые владелец прислал на бат и юань. Скрипт нужен один раз — он
    пропускает валюту, у которой сетка уже заведена, и дальше ставки
    правит администратор в разделе настроек. Где сетки нет, направление
    считается по наценке из предыдущего шага, и это рабочее состояние, а
    не пропуск: у обмена USDT на рубли своя экономика, ступени бата туда
    не переносятся.

Скрипты (`seed-directories`, `set-telegram-webhook`) запускаются с теми же
переменными, что и приложения; на Dokploy это тот же раздел Schedules —
выключенная задача с командой и кнопкой «выполнить». Если база наружу не
открыта, запускать их нужно изнутри контейнера админ-панели —
там уже есть и переменные, и доступ к базе.

### Два контура

Контуров два, и различаются они веткой и ботом, а не кодом:

| | `production` | `dev` |
|---|---|---|
| ветка | `main` | `dev` |
| клиентский бот | `@NemoServiceBTC_bot` | `@devnemobot_bot` |
| база, ключи, секреты | свои | свои, ни один не общий с боевым |

Оба живут на одном Dokploy окружениями одного проекта `nemo` — так их
невозможно перепутать: единственное окружение в панели однажды приняли
за тестовое. Ничего из `dev` не смотрит в боевую базу и не пишет
клиентам боевого бота: у контура свой Postgres, своя пара ключей
реквизитов, свои секреты вебхуков и планировщика.

Путь изменения один: ветка от `dev` → PR в `dev` → сам выезжает на
тестовый контур → проверяется руками через `@devnemobot_bot` →
`pnpm release` → боевой. Релиз — это fast-forward: `main` становится
тем же самым коммитом, что стоит на `dev`, и на прод едет ровно то, что
смотрели, а не «то же плюс коммит слияния». В `main` не коммитят и PR
туда не открывают — он только догоняет `dev`, и git откажет, если
`main` вдруг ушёл вперёд. Обе ветки защищены, и правило действует и
на администраторов: обязательная проверка CI по коммиту, без
force-push. Различие одно: в `dev` изменения принимаются только через
PR, а в `main` требования PR нет — иначе fast-forward отклонялся бы;
проверка считается по коммиту, и у коммита с `dev` она уже есть. Тестовый контур — то место, где смотрят
глазами то, чего не видит ни один прогон: экран, кнопку, ответ бота.

После выката — `GET /api/health` у обоих приложений: `ok`, имя
приложения, коммит сборки и пульс базы. Маршрут открыт без подписи —
по нему же может стучать внешний сторожок раз в минуту — и потому не
говорит ничего сверх этого. Источников курса он не проверяет, а они
умеют молчать при зелёном пульсе: 27 августа 2026 евро и доллар девять
часов стояли без курса при живом `health`. Поэтому после выката ещё и
открыть Mini App и посмотреть пару через стакан — `RUB → EUR`: курс на
черте есть, в журнале контейнера нет строк «не ответила» и «брошен».

У `dev` один бот на всё: клиентский и бот входа в админку — это он же.
Код это допускает — `ADMIN_LOGIN_BOT_TOKEN` не задан, и вход
подписывает клиентский бот, — а виджет Telegram Login привязан к домену
командой `/setdomain` у BotFather на домен тестовой админки. Разделять
боты здесь незачем: ADR-0005 бережёт первый фактор боевого контура, а на
тестовом за ним ничего нет.

Ключа DeepSeek у `dev` нет, и консьерж там молчит — отвечает человек.
Это рабочий выключатель, а не поломка; проверять голос консьержа на
тестовом контуре — задать ключ в переменных окружения `miniapp`.

## Проверки на PR

`.github/workflows/ci.yml` прогоняет на каждом PR то же, что и локально:
типы, миграции на чистой базе, тесты против настоящего Postgres той же
версии, что в `docker-compose.yml`, и сборку обоих приложений.

Сервис развёрнут **временно** на Dokploy: постоянное место зависит от
юрисдикции — того же вопроса, из-за которого не выбран хостинг базы
(блокер A1). Приложения пересобираются по push: `dev` — на тестовый
контур, `main` — на боевой; домены временные, на `sslip.io`, и меняются
вместе с переездом. После смены домена нужно перерегистрировать вебхуки
и повторить `/setdomain`.

## Устройство

- `apps/miniapp` — Telegram Mini App и вебхук бота на grammY.
- `apps/admin` — админ-панель для менеджеров, отдельный деплой.
- `packages/core` — прикладные операции: единственное место, где
  меняется состояние системы.
- `packages/http` — общая обвязка маршрутов обоих приложений: как
  отказы операций превращаются в коды HTTP и как отдаётся JSON, в
  котором есть bigint и денежные строки.
- `packages/telegram` — доставка уведомлений: переходы заявки на обмен
  отправляет админка, регистрацию реферала — Mini App, и клиент должен
  получать их одинаково.
- `packages/db` — схема и доступ к Postgres через Drizzle.
- `packages/types` — доменные типы и денежная арифметика.
- `packages/crypto` — асимметричное шифрование реквизитов.
- `packages/rates` — источники курса: биржи Rapira и Bitkub,
  P2P-раздел HTX, опорные курсы ЕЦБ — реализации интерфейса из
  `@nemo/core`, цепочка из них и составной источник поверх цепочки.
  Отдельным пакетом, потому что провайдеров несколько, а заявка на
  обмен не должна знать, у кого именно спрошена цена
  ([ADR-0007](docs/adr/0007-vtoroy-istochnik-kursa-fiat-cherez-dollar.md));
  снимки держатся тёплыми обновлением по таймеру
  ([ADR-0010](docs/adr/0010-kurs-derzhitsya-tyoplym.md)).

Приложений два, а не одно: приватный ключ расшифровки реквизитов
физически отсутствует в клиентском деплое ([ADR-0002](docs/adr/0002-shifrovanie-rekvizitov-klienta.md)).

## Миграции

```sh
pnpm db:generate          # сгенерировать миграцию по изменениям в схеме
pnpm db:migrate           # применить к базе разработки
pnpm db:studio            # посмотреть данные
```

Схема живёт в `packages/db/src/schema.ts`, миграции — в
`packages/db/migrations`. Правится схема, миграция генерируется по ней;
писать миграцию руками означает разойтись со схемой. Сгенерированной
миграции стоит дать говорящее имя вместо случайного — и в файле, и в
`meta/_journal.json`.

## Скрипты

```sh
pnpm generate-keys            # пара ключей шифрования реквизитов
pnpm create-first-admin       # первый администратор, на пустом списке
pnpm set-telegram-webhook     # регистрация вебхука, см. раздел о ботах
pnpm seed-directories         # справочники: девять валют, направления и сети
pnpm seed-fee-schedules       # ставки по ступеням для бата и юаня
```

Все читают переменные из `.env`, если он есть, и из окружения.
