# «Разработчикам» и «Безопасность» по образцу Love&Pay

Status: resolved (ветка `feature/developer-security-lovepay`, 24 сентября 2026)

## Просьба

Пенкин, 24 сентября 2026, со снимком меню Love&Pay: сделать страницы
групп «Разработчикам» (Документация, API, Вебхуки, API Логи, API
Changelog) и «Безопасность» (Антифрод, KYC, KYC API, Сессии) «не просто
скопировать, а адаптировать и настроить, чтобы всё работало корректно и
правильно с нашей логикой»; полное ревью кода и QA; API и документация
к API.

## Что разобрано у образца

Живой кабинет `app.loveandpay.io` в Chrome Пенкина и
`docs.loveandpay.io` (API v2), 24 сентября 2026. Ничего не нажато,
кроме свёрнутых подсказок и строки журнала.

- **API** (`/api-access`): публичный и секретный ключ, перевыпуск

- **Вебхуки**: подсказка, адреса с событиями, состояние, число

## Что взято и как

| У образца | У нас | Почему так |
| --- | --- | --- |
| Группа «Разработчикам» | Та же, вместо «Интеграции» | Слово образца и просьбы; владелец группу не называл |
| Документация (внешний сайт) | `/docs` из `merchant-v1.yaml` + разделы «Подпись», «Пределы», «Коды ошибок» | Договор один и сверяется тестом с маршрутами |
| API: ключи | Ключи как были: несколько, отзыв по одному, показ один раз | Пара «публичный + секретный» ничего не добавляет: у нас подпись считается тем же ключом |
| Проверки запроса | Карточка: подпись и разрешённые адреса — включены ли | Сертификата нет (см. ниже) |
| Ограничения | Карточка: пределы из кода + сколько раз упёрлись за сутки | Числа из `RATE_LIMITS` и журнала, не выдуманные |
| Разрешённые адреса | То же: IP или подсеть, заметка, когда добавлен; пустой список — с любого адреса | Украденный ключ бесполезен вне серверов мерчанта. Адрес за Traefik подделать нельзя — он вычищает `X-Forwarded-For` недоверенных клиентов |
| Пример подписи | Node.js, Python, PHP, curl | Примеры проверены против `verifySignature` |
| `X-RateLimit-*`, идентификатор запроса | Заголовки на каждом ответе с узнанным ключом, `x-request-id` на каждом | Лучшая практика; идентификатор — в журнале и в карточке |
| API Логи | «Журнал вызовов»: + метод, поиск по пути, адрес клиента, карточка вызова | Название прежнее: «логи» — заимствование, а раздел уже так назван |
| Тела запроса и ответа в карточке | Нет | В телах реквизиты получателей; открытым текстом их в клиентском контуре не держим (ADR-0002) |
| API Changelog | «Изменения API»: записи с датами из истории договора | У нас изменения были, и мерчанту их видно |
| Сессии | То же: устройства человека, отключить одно, отключить все, кроме этого | Сессия теперь запись в базе; поколение осталось — смена пароля обрывает всё разом |

## Что не взято

- **Антифрод по чекам, KYC, KYC API.** Сервис не принимает деньги
  покупателей мерчанта, плательщика нет — сверять нечего и проверять
  некого. Экран из нулей обещал бы то, чего сервис не делает.
- **Подтверждённые домены (TXT).** Вызовы API идут с серверов мерчанта,
  домен в них ничего не удостоверяет; адрес — удостоверяет.
- **API v3 с сертификатами и шифрованием тела.** TLS плюс HMAC; второй
  контур со своими ключами — работа без выигрыша при нашем объёме.
- **Блокировка за одинаковые запросы (CYCLE_BLOCKED).** Повтор подачи
  закрыт ключом повтора, частота — пределом.
- **Перевыпуск секрета одной кнопкой.** Отзыв и выпуск нового —
  тот же результат, и в журнале остаётся, каким ключом что подавали.

Всё это — в `backlog.md` с причиной.

## Решения по ходу

- Идентификатор запроса выдаёт сервер (`crypto.randomUUID`), присланный
  клиентом не принимается: чужой мог бы совпасть или подменить.
- `x-ratelimit-reset` — время ISO, когда откроется ограничивающее окно:
  часовое, если час исчерпан, иначе минутное.
- Разрешённые адреса проверяются после узнавания ключа: отказ — 403
  `address_not_allowed` и пишется в журнал (ключ узнан, и мерчанту
  видно, с какого адреса пытались).
- Сессия в куке: `userId.sessionId.expiresAt.подпись`; запись в базе
  несёт поколение. Старые куки (без номера сессии) не читаются — после
  выката все входят заново. На проде мерчантов нет, на dev — демо-входы.
- «Была активность» обновляется не чаще раза в пять минут — как отметка
  последнего вызова ключа.
- Названия. Владелец эти разделы не называл, просил Пенкин «как у
  них», поэтому слова образца взяты там, где они русские и понятные:
  «Разработчикам», «Безопасность», «Сессии», «Проверки запроса»,
  «Ограничения», «Была активность», «Всего записей». Свои оставлены там,
  где у образца заимствование: «Журнал вызовов» вместо «API Логи»,
  «Изменения API» вместо «API Changelog».
- «Откуда звали за сутки» предлагает «Разрешить» только адресу, который
  хоть раз пропустили на входе — прошёл ключ, подпись и список, чем бы ни
  кончился дальше (422 — это наш сервер, дошедший до правила): вор с
  утёкшим ключом стоит в том же списке, и отличает его только это (ревью).
- Отказы по адресу пишутся в журнал не больше десятка за четверть часа
  с пары «ключ и адрес»: запирать адрес счётчиком нельзя — владелец
  добавит свой забытый сервер, а тот ещё 15 минут ловил бы 429 (ревью).

## Открытый вопрос — решение за Пенкиным

**Защита от повтора подписи отвергает честные одинаковые запросы.**
Метка времени в секундах, и два одинаковых запроса в одну секунду —
например, параллельный опрос `GET /exchange-requests?limit=50` двумя
воркерами — подписываются одинаково; второй получает `401 «Эта подпись
уже была»`. Найдено на QA: Node- и Python-примеры, запущенные подряд.
Правило старое (с 7 сентября), не этой ветки.

Варианты: (а) не проверять повтор у `GET` — чтение ничего не меняет, а
подача и так защищена `Idempotency-Key`; плата — перехвативший
подписанный `GET` может прочитать тот же ответ ещё раз в течение пяти
минут; (б) принимать `x-timestamp` и в миллисекундах — совпадения
станут редкими, но не исчезнут; (в) оставить и написать в документации.
Рекомендация — (а): так устроены подписи у Binance и Coinbase (только
окно времени), а изменяющие запросы останутся под защитой.
