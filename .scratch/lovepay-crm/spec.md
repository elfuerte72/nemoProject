# Спека: перенос устройства кабинета Love&Pay в панель менеджера

Дата: 2 сентября 2026. Основание — просьба владельца изучить
app.loveandpay.io и «взять все фишки» для нашей CRM-панели (`apps/admin`).

Источники: живой обход кабинета Love&Pay через Chrome
(`.scratch/lovepay-crm/research-lovepay.md`), полная разведка `apps/admin`
и полная разведка `packages/core`/`packages/db`/`packages/types`
(агенты Explore, 2 сентября 2026, результаты в истории сессии
`session_01VZf5FJCpyFXcgKUMbCCm9Y`).

## Зачем

Love&Pay — кабинет мерчанта платёжного сервиса (счета, СБП, KYC).
nemoProject — обменник с заявками и менеджерами. Сущности не совпадают
один в один, но **устройство** кабинета — экраны, разрезы, подсказки,
настройки таблиц, сессии — переносится почти целиком, а часть разделов
(POS-касса, KYC, антифрод, фискализация, API v3, криптообмены как
продукт) не переносится за отсутствием аналога в нашей модели.

## Что уже есть в `apps/admin` (не изобретать заново)

- Очередь заявок с курсорной пагинацией в ядре (`ExchangeQueueFilter`),
  фильтры в адресе, «моё/чужое/все», карточка заявки с лентой событий,
  раскрытие реквизитов с журналом доступа, тихое автообновление
  (`lib/live.ts`), переписка с клиентом, настройки (сетки комиссий,
  направления, сети, сотрудники, база знаний консьержа, рассылки),
  счета сервиса.
- Готовые примитивы CSS: таблица-список (`table`/`table__row`/`cell`),
  пилюли (`pillClass`), кнопки (`btn--gold/soft/ghost/danger`), поля
  форм, фильтры-чипы, `HowToRunRequest`, `LiveQueue`, `Moment`,
  `CopyValue`, `ClientCard`.
- Токены `globals.css` те же, что в Mini App — переиспользуются
  напрямую, ничего не заводится заново.
- Полный отчёт с путями файлов и списком классов — в истории сессии
  (агент «Разведка apps/admin», 2 сентября 2026); при реализации сверяться
  с ним, а не пересматривать код заново.

## Что уже есть в ядре (без изменения схемы)

Список операций, форм фильтров, счётных запросов и мест агрегации —
в отчёте агента «Разведка ядра и схемы» (история сессии, 2 сентября
2026). Коротко: есть очередь/count по заявкам, `getClientCard`,
`listStaff`, история заявки, журнал доступа к реквизитам (только
фильтр, без курсора), баланс баллов, очередь выводов, очередь заявок на
карту. **Агрегации по деньгам (оборот, доход, конверсия, средний чек,
время в состоянии) нигде не считаются** — данные в `exchange_requests`
и `exchange_request_events` есть, чтения нет.

## Три уровня работ

### Уровень 1 — паттерны интерфейса, готовые данные, без изменений в ядре

Только `apps/admin` (разметка, CSS, клиентские компоненты), данные уже
есть операциями. Можно начинать сразу.

1. **Обзор-дашборд на `/`** вместо прямого захода в стол. KPI-плитки
   (заявок сегодня, в очереди, отвечено обращений — уже считаются),
   быстрые действия, полоса состояния. Взамен текущего рабочего стола
   или как отдельная стартовая страница.
2. **Подсказка «Как устроено»** — свёрнутый блок с объяснением правил
   на разделах, где её ещё нет (`withdrawals`, `card-applications`,
   `service-accounts`, `requisite-access`) — по образцу уже готового
   `HowToRunRequest`.
3. **Личные настройки таблицы** (колонки, плотность, строк на
   странице) — по образцу Love&Pay «Поля», хранить в `localStorage`
   браузера менеджера, как у них.
4. **Раздел «Сессии»** сотрудника — таблица активных входов «это
   устройство» / «Отключить» — **требует новой таблицы** (см. уровень 3,
   но UI-паттерн описываю здесь для контекста).
5. **Палитра ⌘K** — быстрый переход к заявке/клиенту по номеру или нику.
   Данные есть (`filter.query`), нужно только собрать компонент.
6. **Курсорная подгрузка «показать ещё»** в очередях — курсор уже есть
   в `ExchangeQueueFilter`, панель его не использует (сейчас —
   «показаны первые N из M»). Ticket уже был предложен в
   `admin-manager-ux`, не сделан.
7. **Передача заявки другому менеджеру** — UI есть куда добавить
   (карточка заявки), но операции `reassignExchangeRequest` в ядре
   нет — см. уровень 2.

### Уровень 2 — новые операции чтения над существующими таблицами

Ядро приобретает агрегирующие запросы, схема не меняется. Каждая — с
падающим тестом на настоящей базе (`CLAUDE.md`, порядок работы с
тестом).

1. **Раздел «Аналитика»**: оборот/доход/конверсия/средний чек за
   период со сравнением с предыдущим равным периодом (как у Love&Pay);
   разрез по дням, по менеджерам, по направлениям; воронка заявок
   (`new → in_progress → rate_confirmed → payment_received →
   completed`, отдельно `cancelled`) — считается `group by status,
   date_trunc`. Требует: `listExchangeRequestStats(actor, {from, to,
   groupBy})` или похожую операцию.
2. **Время в состоянии / время до оплаты** — есть в
   `exchange_request_events` (переходы с `created_at`), нужна операция,
   считающая разницу между событиями по заявке или партиями.
3. **Раздел «Клиенты»** как список (не только карточка): нужна
   `listClients(actor, filter)` — по нику/id, с оборотом (сумма
   `service_income` или `from_amount` по завершённым заявкам клиента),
   числом заявок, датой регистрации, уровнем (по Love&Pay — можно
   заменить на «постоянный клиент» по числу оплат, без формальных
   уровней доверия — у нас нет KYC). Обязательно — `limit`/курсор.
4. **`reassignExchangeRequest`** — операция передачи заявки другому
   менеджеру (сейчас `requireOwnership` не даёт обхода даже админу —
   явно отмечено в коде как отложенное).
5. **Отчёты по сотрудникам** — кто сколько заявок взял/закрыл,
   конверсия, средний чек, оборот за период — тот же `group by
   assigned_manager_id`.
6. **Реферальная сводка одной страницей** — свести `getBonusAccount`,
   ставки, историю начислений и открытые выводы в один экран по
   образцу «Комиссии» Love&Pay (плитки со ставками + детализация по
   сети). У нас реферальная логика уже полнее их (две линии, выплата
   баллов существует как заявка) — просто не собрана в одну сводку.
7. **Курсор/limit** там, где их сейчас нет и список может вырасти:
   `listConversations`, `listRequisiteAccessLog`, `listWithdrawalQueue`,
   `listCardApplicationQueue`.

### Уровень 3 — новая схема

Требуют новых таблиц, миграций, ADR при необходимости.

1. **Сессии сотрудников как таблица** — сейчас сессия целиком в
   подписанной куке (`apps/admin/lib/auth/session.ts`), отзыв доступа
   уже работает через `staff.is_active` (проверяется на каждом
   запросе — этого достаточно для «выключить сотрудника»). Раздел
   «Сессии» с перечислением устройств и точечным «Отключить именно это
   устройство» **не обязателен функционально** (`setStaffActive`
   решает ту же задачу грубее), но если делать как у Love&Pay —
   нужна таблица `staff_sessions` и разворот куки в неё. **Открытый
   вопрос владельцу**: нужна ли точность до устройства, или хватает
   «выключить сотрудника целиком» (уже есть).
2. **Снимки курса в базе (история курса)** — у нас `packages/rates`
   держит кэш в памяти процесса (namespace snapshots), у Love&Pay —
   таблица с историей по парам. Если нужен раздел «Курсы» с историей
   и наценкой по времени — снимки придётся класть в таблицу при
   каждом обновлении (или хотя бы периодически). Сейчас это не нужно
   ядру для работы — вопрос ценности отдельного раздела истории курса
   для менеджера.
3. **Агрегатные таблицы для аналитики** (если чтения `group by`
   поверх `exchange_requests` станут медленными при росте) — не сейчас,
   `CLAUDE.md`: «тяжёлое (аналитика) не делается, пока нет чисел».

## Что не переносится

POS-касса как отдельный продукт (у нас заявку не выставляют «на
кассе» — это чужая бизнес-модель приёма платежей), KYC/антифрод
(нет провайдера и нет решения владельца о его найме), фискализация
(нет кассового обслуживания в этом контуре), API v3/сертификаты,
криптообмены как отдельный продукт (частично покрыто нашими же
заявками), вебхуки для внешних интеграторов (некому интегрироваться —
мы не платформа для третьих лиц), реферальные «отдельные кабинеты»
(под-партнёры со своим API — не входит в модель).

## Порядок предложен

1. Уровень 1, пункты 1–3, 5–6 — чистая разметка/клиентский код, можно
   делать пачкой без риска для ядра.
2. Уровень 2, пункт 4 (`reassignExchangeRequest`) — маленькая, снимает
   реальное неудобство («заявка зависла на ушедшем менеджере»).
3. Уровень 2, пункты 1–2 (аналитика/время в состоянии) — самая
   ценная часть просьбы «как у Love&Pay», но и самая объёмная: новая
   операция, новый раздел, тесты агрегации.
4. Уровень 2, пункт 3 (клиенты) — вторая по ценности; нужна для
   «повторные клиенты», о чём Love&Pay явно пишет в аналитике.
5. Уровень 2, пункты 5–7 — по мере необходимости.
6. Уровень 3 — только по решению владельца, после уточняющих вопросов
   ниже.

## Решения

Приняты 2 сентября 2026 — владелец отдал выбор разработчику («полная
свобода идей»). Каждое можно пересмотреть, но тикеты написаны по ним.

1. **Порядок:** уровень 1 (тикеты 01–05) → передача заявки (06) →
   аналитика (07, 08) → клиенты (09) → реферальная сводка (10).
   Тикеты 01, 05, 03 трогают одни файлы стола — в одной сессии идут
   цепочкой в этом порядке.
2. **Обзор — на той же странице `/`,** полосой над столом, а не
   отдельной стартовой: стол отвечает на вопросы смены по порядку, и
   отодвигать его на клик ради плиток нельзя. Числа «за сегодня»
   (исполнено, отменено, оборот) требуют операции подсчёта — она
   появляется в тикете 07, и тогда же обзор получает строку «Сегодня».
3. **⌘K** в уровне 1 ищет открытые заявки по нику/ID клиента и
   прыгает по полному ID заявки или клиента. Поиск по всем состояниям
   и по клиентам приходит с тикетом 09.
4. **Деньги никогда не суммируются через валюты.** Оборот и доход
   показываются по каждой валюте отдельно («12 300 RUB · 450 USDT»):
   исторического курса у нас нет, а приведённое к одной валюте число
   читалось бы как факт. Это правило и для аналитики, и для клиентов.
5. **Аналитика — только администратору.** Доход сервиса — экономика,
   которую сейчас видит только он (настройки). Менеджеру отказ
   объясняется заглушкой, как в настройках. Менеджер видит свои
   числа в «Обзоре» (счётчики, «сегодня») — там нет денег сервиса.
6. **Периоды аналитики:** Сегодня, 7 дней, 30 дней, 90 дней, свой
   период; сравнение — с таким же по длине периодом прямо перед
   выбранным (как у Love&Pay). Заявки считаются по дате подачи, доход
   — по дате исполнения.
7. **Клиенты — обеим ролям.** Колонки: ник/ID, в сервисе с, заявок
   (исполнено/отменено), последняя заявка, оборот по валютам (сумма
   `from_amount` исполненных, по `from_code`). Метка «постоянный» —
   от трёх исполненных заявок; это не уровень доверия и не KYC, а
   подсказка менеджеру «с этим человеком уже работали».
8. **Передача заявки:** администратор передаёт любую; ведущий менеджер
   может передать свою коллеге. Забрать чужую самому — нельзя, это
   правило владения из `requireOwnership`. Клиенту уведомление не
   уходит — его процесс не меняется; в историю заявки пишется событие
   с именем нового менеджера.
9. **Уровень 3 не делается:** сессии по устройствам — выключить
   сотрудника целиком уже работает и закрывает доступ немедленно;
   история курса в базе — раздел без запроса от менеджера.
10. **Ветка одна — `feature/crm-panel`,** коммит на тикет, PR в `dev`
    по завершении уровня 1; уровень 2 — вторым PR с той же ветки после
    слияния первого.
11. **Дизайн — по образцу Love&Pay** (просьба владельца 2 сентября
    2026): боковое меню с группами и свёртками, шапка с поиском и
    подписью сотрудника, единая анатомия страницы (заголовок +
    подзаголовок слева, действия справа, подсказка «как устроено»,
    полоса плиток KPI, табы состояния со счётчиками, таблица, подвал
    пагинации), карточки на тёмных поверхностях, пустые состояния с
    иконкой и действием. **Палитра остаётся фирменной** — индиго под
    медовым акцентом из `theme/`, как требует `CLAUDE.md`: у Love&Pay
    синий акцент, у нас золото играет ту же роль. Примитивы заводятся
    одним тикетом до всех остальных: они нужны каждому экрану.

## Критерии готовности

По каждому тикету — свой, но на весь этап 1 (уровень 1) в целом:

- Обзор-дашборд открывается на `/`, показывает реальные счётчики
  (не заглушки), собран теми же операциями, что уже дёргает
  `app/(panel)/layout.tsx`.
- Подсказки «Как устроено» добавлены на всех перечисленных разделах,
  свёрнуты по умолчанию, текст выверен как остальной голос панели
  (`bot-slop.ts` их не коснётся — они не исходящие сообщения клиенту,
  но длинного тире через связку в одном абзаце в них тоже быть не
  должно, ради единого голоса).
- Личные настройки таблицы переживают обновление страницы и не текут
  между сотрудниками (ключ `localStorage` содержит `staffId`).
- ⌘K находит заявку по номеру/фрагменту и клиента по нику за один
  запрос к уже существующему `filter.query`.
- «Показать ещё» в очередях использует курсор `ExchangeQueueFilter.after`
  вместо чтения всего списка разом; на 200+ заявках в статусе не
  подтормаживает (курсорные индексы уже заведены).
- Ни один тикет уровня 1 не меняет `packages/db/src/schema.ts` и не
  добавляет миграцию.
- `pnpm typecheck` и `pnpm --filter @nemo/admin run test` зелёные;
  новых предупреждений ESLint/TS не появляется.

Для уровня 2 (когда до него дойдём) — каждая новая операция ядра
начинается с падающего теста на настоящей базе, как того требует
`CLAUDE.md`.

## Границы

- **Всегда:** для новых операций ядра — тест первым (`CLAUDE.md`,
  «Порядок работы с тестом»); классы CSS брать из уже существующего
  набора `apps/admin/app/globals.css`, не заводить параллельных
  примитивов; фиксировать сделанное в `CHANGELOG.md` тем же коммитом.
- **Спросить сначала:** любая миграция `packages/db` (новая таблица —
  `staff_sessions`, таблица снимков курса и т.п.); смена роли доступа
  (кто видит раздел «Клиенты» — только админ или обе роли); удаление
  или переименование существующих операций/маршрутов.
- **Никогда:** не заводить второй справочник текстов/подсказок в базе
  (решение уже принято и записано в `CLAUDE.md` — заготовки живут в
  коде, не в панели администратора, кроме базы знаний консьержа);
  не показывать в «Клиентах» ничего похожего на KYC-статус без явного
  решения владельца; не трогать `packages/rates` ради истории курса,
  пока не решено, что раздел вообще нужен.
