# Список заявок: поиск по своему номеру

Status: ready-for-agent
Раздел: Заявки

Главный путь в список заявок начинается не с «посмотреть, что в
работе», а с конкретной заявки: покупатель пишет мерчанту «заказ 1013,
где деньги», и мерчант идёт её искать. Сегодня искать нечем — есть табы
состояния и прокрутка, и сотую заявку находят кнопкой «Показать ещё»,
нажатой четыре раза.

## Что сделать

Ядро: у `listExchangeRequests` и `countExchangeRequests` — отбор по
своему номеру (`reference`). Совпадение по началу и по вхождению, без
учёта регистра. Сравнение — с `collate "und-x-icu"`: база собрана с
локалью `C`, и обычный `ilike` кириллицу по регистру не сводит — на этом
уже спотыкался поиск мерчантов в панели. Наш идентификатор заявки,
набранный целиком, тоже находит её: из письма и из вебхука копируют
именно его.

Кабинет: поле поиска над табами. Запрос живёт в адресе (`?q=`), как таб
и период: сужать выборку должен сервер, иначе «поиск» означал бы, что
приехало всё, а часть спрятана разметкой, — и дочитывание по курсору
обязано искать тем же отбором, что и первая страница (правило одно,
`lib/request-rows.ts`). Счётчики табов при поиске считают найденное, а
не всё: иначе «Исполнены 10» над двумя строками.

Поиск идёт по всем состояниям сразу, а не внутри открытого таба: ищущий
«заказ 1013» не знает, исполнен он или отменён, — за этим и пришёл.

Пустой ответ говорит, что делать: «Заявки с таким номером нет.
Проверьте номер — он тот, который ваша система передала при подаче».

## Порядок работы

С падающего теста на ядро: кириллический номер находится в любом
регистре, чужая заявка не находится никогда, курсор с отбором не теряет
и не дублирует строк.

## Чего здесь не будет

Поиска по сумме, получателю и дате — пока не попросят. Период и
направление уже есть разрезами в аналитике, а поле, которое ищет «по
всему», перестаёт отвечать внятно, по чему оно нашло.
