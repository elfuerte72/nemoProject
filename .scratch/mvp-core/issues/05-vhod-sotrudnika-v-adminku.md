# 05 — Вход сотрудника в админ-панель

**What to build:** менеджер входит в админку через Telegram, без отдельного пароля, но с обязательным вторым фактором. Доступ получают только те, кто заведён в списке сотрудников.

**Blocked by:** 01

**Status:** ready-for-agent

- [x] Вход выполняется через Telegram Login, подпись проверяется
- [x] Допуск получают только сотрудники из списка; остальные получают отказ без подсказок о том, что именно не так
- [x] Второй фактор обязателен: без подтверждения кодом сессия не выдаётся
- [x] Отключённый сотрудник теряет доступ немедленно, не дожидаясь истечения сессии
- [x] Сессия истекает по времени и требует повторного входа
- [x] Подпись, сделанная по схеме Mini App, для входа в админку не принимается — схемы подписи у клиентской и служебной частей разные

## Comments

Сессия админки покрыта тестами (`apps/admin/lib/auth/session.test.ts`),
хотя спека называет единственным seam-ом `@nemo/core`. Это тот же род
проверки, что и уже существующие тесты подписи Telegram Login и данных
запуска Mini App: чистая функция с краевыми случаями — чужой секрет,
истёкший срок, подделанная ступень входа, — а не маршрут и не
компонент. Ровно эти случаи спека и называет достойными покрытия.

Известное ограничение, и оно шире, чем кажется. Секрет второго фактора
заводится сам при первом входе — по одной лишь подписи Telegram Login, —
и сбросить его нечем. Отсюда две беды. Потерявший телефон сотрудник войти
не сможет. И, что серьёзнее, аккаунт, угнанный до первого входа, позволяет
вору завести собственный аутентификатор: второй фактор не срабатывает
ровно в том случае, ради которого заведён (история 40 спеки).

Формально критерий тикета выполнен — без кода сессия не выдаётся, — и
пока в системе нет ни одного сотрудника, воровать нечего. Но выдавать
секрет должен администратор, а не первый предъявитель подписи. Это
работа тикета 14, где администратор и заводит сотрудников; пункт туда
добавлен.
