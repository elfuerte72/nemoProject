# Реферальная программа настраивается: глубина, уровни, личные ставки, несколько кодов

Сколько линий сервис оплачивает и по какой ставке, задаёт администратор списком линий — до пяти. Поверх базовых ставок действуют уровни по числу активных рефералов и личные ставки клиента; ставка линии берётся по старшинству «личная → уровень → базовая» в момент исполнения заявки. Кодов у клиента несколько — ссылки и промокоды — и они живут таблицей, а не колонкой.

## Context

До 8 сентября 2026 программа была жёсткой: ровно две линии, ставки двумя колонками `service_settings`, один код в `clients.referral_code`, привязка реферера только при первом запуске по ссылке. Владелец попросил «гибче»: партнёру с блогом — свой процент, крупному — уровень, а не разговор о ставке каждый раз; несколько ссылок, чтобы видеть, откуда приходят; промокод словом, который называют голосом; глубина больше двух. Правило вознаграждения от дохода по заявке (docs/adr/0003) при этом не пересматривается.

## Decision

**Цепочка хранится на всю возможную глубину, платится по настроенной.** При регистрации по коду в `referrals` пишутся строки на каждого предка до пятой линии (`MAX_REFERRAL_DEPTH`), обходом по `clients.referrer_id` внутри транзакции. Начисление идёт по линиям не глубже числа строк в `referral_line_rates` на момент исполнения. Так администратор, углубивший программу позже, не обнаруживает, что у старых цепочек третьей линии нет. Глубже пяти не платится никогда: это предел схемы, а не настройка.

**Три источника ставки, старшинство по каждой линии отдельно.** Личная ставка клиента (`client_referral_rates`), ставка его уровня (`referral_tier_rates`), базовая ставка линии. Считает одна функция — `effectiveReferralRates` — и для начисления, и для показа клиенту: ставка на экране и ставка в начислении не должны разойтись. Ставка каждого начисления по-прежнему пишется в строку движения: прошлое от смены настроек не меняется.

**Уровень — по активным рефералам первой линии.** Порог уровня — число приведённых самим клиентом, у которых есть хотя бы одна исполненная заявка; берётся самый высокий из достигнутых, и уровень пересчитывается в момент каждого начисления. Порог по обороту рефералов не берётся: оборот идёт в разных валютах, а складывать их нельзя (docs/adr/0013), и исторического курса у сервиса нет. Свой реферал становится активным своей же первой исполненной заявкой — уровень достигнут в момент её исполнения, и начисление по ней уже идёт по уровню.

**Коды — таблица `referral_codes`.** Вид `link` со сгенерированным кодом и вид `promo` со словом клиента (4–16 знаков, латиница и цифры, без учёта регистра, слова сервиса из стоп-списка не отдаются); у каждого название, до десяти действующих, архив вместо удаления — на код ссылаются приведённые им клиенты (`clients.referred_via_code_id`). Последняя действующая ссылка не архивируется: её шлёт бот и лист «Пригласить». Колонка `clients.referral_code` остаётся на одну выкатку неиспользуемой: Mini App старой сборки читает её до своей пересборки, и удалить её той же миграцией значило бы уронить котировки на минуты выката. Удаляется следующей миграцией.

**Промокод после регистрации — только пока клиент чист.** `bindReferrerByPromoCode` привязывает реферера тому, у кого ещё нет ни реферера, ни заявок на обмен. Клиент с заявками — уже клиент сервиса, и приписывать его рефереру задним числом значило бы платить за того, кого никто не приводил. Свой код и код своего реферала не привязывают: второе замкнуло бы цепочку в кольцо. Вводится в Mini App; бот `/start <код>` по-прежнему не разбирает — там `telegram_user_id` не подтверждён подписью initData.

**Правка баллов руками — движение `adjustment`** с обязательным комментарием и подписью сотрудника; снять ниже нуля нельзя. Нужна рядом с личными ставками: там, где ставку назначили руками, ошибку правят тоже руками.

## Consequences

- Ставки линий уходят из схемы `service_settings`, код клиента — из схемы `clients`; сами колонки снимает следующая миграция после выката. Всё, что про программу, — линии, уровни, личные ставки, правка баллов, — пишется в журнал настроек своими темами (`referral_line_rates`, `referral_tier`, `client_referral_rates`).
- Клиент, заведённый старой сборкой Mini App в окно выката, остаётся без строки кода: основной код ему заводится при первом чтении (`primaryReferralCode`), а не отказом.
- Начисление стало на запрос дороже: для каждого предка считаются его личные ставки, уровень и число активных рефералов. Заявок десятки в день, предков не больше пяти — это не стоит кэша.
- Тексты, называющие линию словом, принимают линию 1..5 (`referralLineWord`, `referralLineName`); «второй» больше не единственный вариант.
- Уровень в строке начисления не записан — только ставка. Клиент видит, по какой ставке начислено, но не по какому уровню; запись в `backlog.md`.
- Порог уровня иного рода — по обороту, по числу заявок, — потребовал бы отдельного решения о том, что считать величиной.
