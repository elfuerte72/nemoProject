# Реквизиты клиента хранятся зашифрованными, а не маскированными

Раздел 9 ТЗ рекомендует не хранить полный номер карты клиента либо хранить его маскированным. Оба варианта ломают фичу из п. 4.2.4: сохранённые реквизиты нужны, чтобы менеджер **отправил** клиенту деньги, а по маскированному номеру перевод сделать нельзя — клиенту пришлось бы диктовать номер при каждой заявке. Поэтому полный номер хранится в базе зашифрованным (ключ вне базы), клиент видит маску вида `**** 4821`, менеджер получает полный номер только при открытии конкретной заявки, и каждый такой доступ пишется в журнал.

## Consequences

Хранится номер карты **получателя** — без CVV и без срока действия, то есть данные, по которым можно только зачислить средства, но не списать. Это сознательное отклонение от рекомендации ТЗ: следующий разработчик, увидев зашифрованный PAN, не должен «исправлять» его на маску. Решение дорого разворачивать после накопления данных — потребуется миграция и повторный сбор реквизитов у клиентов. Статус `proposed` — выносится на согласование с заказчиком.
