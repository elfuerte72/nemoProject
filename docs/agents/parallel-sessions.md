# Несколько агентов в одном проекте

Как вести две и больше сессий одновременно, чтобы они не ломали друг
друга и чтобы принимать их работу можно было по очереди, а не
разбираться в мешанине.

Записано по следам 7 августа 2026, когда две сессии работали в одном
рабочем каталоге: одна правила панель менеджера, другая — тексты бота.
Обошлось, но не потому, что процесс был устроен верно.

## Что ломается на самом деле

Конфликт git безобиден: он останавливает слияние и зовёт человека.
Ломает то, что сливается молча.

- **Семантический конфликт.** Один агент переименовал функцию, другой в
  своей ветке добавил её вызов. Оба PR зелёные по отдельности, вместе
  не собирается. Git тут не спорит — спорить не о чем, строки разные.
- **Общий файл-регистр.** `CHANGELOG.md`, `packages/core/src/index.ts` —
  места, куда пишут все. Git сольёт две записи без вопросов. В тот день
  запись соседа о текстах бота уехала в прод вместе с чужим PR, а код к
  ней остался незакоммиченным: полтора часа журнал обещал то, чего в
  сервисе не было.
- **Номера миграций.** Drizzle нумерует их подряд. Две ветки, начатые от
  одного места, обе сгенерируют `0016_*`, и конфликт будет не только в
  файлах, но и в `_journal.json`. Разрешённый неверно, он даёт схему,
  разъехавшуюся с кодом, — и узнают об этом на проде.
- **Чужой незакоммиченный код в прогоне.** Тесты в общем каталоге видят
  и вашу работу, и соседскую. Зелёный прогон тогда не значит ничего.

## Каталог на сессию

Один каталог на две сессии — источник всего перечисленного. Разводится
рабочими деревьями: общий `.git`, разные каталоги и ветки.

```sh
git worktree add ../nemo-texts -b feat/bot-texts main
cd ../nemo-texts && pnpm install
```

Для этого проекта в каждой сессии сверх того:

- **своя тестовая база.** `TEST_DATABASE_URL` со своим именем — иначе
  `pnpm test` в двух сессиях вычищает данные друг у друга, и падения
  выглядят как ошибки в коде, хотя код ни при чём;
- **свой порт.** `next dev` у панели занимает 3001, у Mini App 3000.

Дерево убирается, когда ветка слита: `git worktree remove ../nemo-texts`.

## Как резать задачи

Резать по швам, а не по файлам, и до того, как сессии запущены. Признак
хорошего разреза: два агента не открывают один файл.

Плохой разрез — «один делает фичу, другой рефакторит то же место». Это
не параллельная работа, а гонка, и переделка достанется тому, кто
мержится вторым.

Полностью развести не выйдет: файлы-регистры есть по устройству. С ними
два выхода — либо принять, что конфликт там текстовый и разрешается
руками за минуту, либо не давать двум сессиям одновременно задачи,
которые обе туда пишут.

**Схему в один момент времени меняет одна ветка.** Если так не вышло,
тот, кто мержится вторым, удаляет свою миграцию и генерирует заново
поверх обновлённого `main` — вместе с записью в `_journal.json`.

## Проверка ветки на слиянии, а не саму по себе

В защите ветки `main` включено `strict` у обязательных проверок. Это
значит, что перед слиянием ветка обязана подтянуть `main`, и CI гоняется
заново — уже на том, что получится после мержа.

Без этого каждый PR проверяется на своей базе, и семантический конфликт
доезжает до `main` незамеченным. С этим — второй PR после мержа первого
обязан пересобраться, и конфликт всплывает в CI, а не в проде.

```sh
gh api -X PATCH repos/<owner>/<repo>/branches/main/protection/required_status_checks -F strict=true
```

## Порядок приёмки

Не в порядке готовности, а снизу вверх: сначала то, что трогает
фундамент — схему, ядро, общие типы; потом надстройки. Смерженная
наоборот надстройка встаёт на старый фундамент и падает при следующем
мерже.

После каждого слияния остальные ветки подтягивают `main` и
перепрогоняются. С включённым `strict` это происходит само.

## Чем проверять

Пять рубежей, каждый дешевле следующего.

1. **У себя.** `pnpm typecheck && pnpm test` перед коммитом.
2. **CI на PR.** Типы, миграции на чистой базе, тесты, сборка — уже
   настроено в `.github/workflows/ci.yml`.
3. **В изоляции, если в дереве есть чужое.** Прогон в общем каталоге
   врёт: он видит чужой незакоммиченный код. Проверяется свой коммит
   отдельным деревом:

   ```sh
   git worktree add /tmp/verify HEAD
   cd /tmp/verify && pnpm install && pnpm test
   ```

4. **На тестовом контуре — глазами.** PR идёт в `dev`, а не в `main`;
   слитое само выезжает на тестовый контур, и там через
   `@devnemobot_bot` смотрят ровно то, что менялось, тем способом,
   каким этим пользуются. Только после этого — PR из `dev` в `main`.
   Устройство контуров — в README, раздел «Два контура».

5. **После выката — smoke.** Пара запросов по живым адресам: отвечает ли
   приложение, появился ли новый раздел, отвечает ли отказом то, что
   должно быть выключено в проде.

## Выкат, когда миграция трогает общую таблицу

Схему делят оба приложения, а мигрирует только админка при старте
(`docker/admin.Dockerfile`). Drizzle перечисляет колонки явно, поэтому
Mini App, поднявшийся на новом коде до миграции, падает на каждом
запросе к изменённой таблице. По push оба стартуют разом, и Mini App
исторически собирается быстрее — то есть в самом опасном порядке.

Порядок: снять автодеплой с Mini App, смержить (поедет одна админка и
накатит миграции), дождаться нового кода на её домене, выкатить Mini App
вручную, вернуть автодеплой. Подробности — в памяти сессии про Dokploy.

## Что остаётся человеку

Агенты пишут код, но принимает его человек, и приём — не чтение дифа
целиком.

- **PR должен быть маленьким.** Ветка живёт часы, а не дни: чем дольше,
  тем дальше она уезжает от `main` и тем меньше шансов, что расхождение
  заметят до слияния.
- **Описание объясняет «почему».** Если из него не видно, почему сделано
  так, — это сигнал, что агент не понимал, что делает, и диф читать
  придётся целиком.
- **Найденное на ревью становится тестом.** Замечание, не закреплённое
  тестом, возвращается через месяц — и первым это замечает тот, кто по
  нему работает.
