# Техническое задание (черновик v0.3)
## Telegram-бот + админ-панель для сервиса обмена валют

**Статус документа:** черновик, готовность ~32%.
**Назначение:** база для созвона с разработчиком и предварительной оценки. **Не** финальное ТЗ — содержит открытые вопросы (см. раздел 12), которые нужно закрыть до старта разработки.

---

## 1. Краткое описание продукта

Сервис для обмена валют (фиат ↔ криптовалюта ↔ наличные), работающий через Telegram-бота. Бот выполняет роль **консьержа и приёмника заявок**: приветствует клиента, собирает запрос на обмен, показывает предварительный курс и передаёт заявку менеджеру. Всё исполнение сделки (приём оплаты, выдача реквизитов, финальный расчёт) выполняется **менеджером вручную** через админ-панель.

Дополнительно: реферальная программа на 2 уровня, заявки на выпуск европейской карты, автоматизированная поддержка на базе знаний, рассылки с согласия клиента. В перспективе — интеграция с CRM для аналитики поведения клиентов.

---

## 2. Ключевые архитектурные принципы (критичные, не подлежат нарушению)

1. **Бот и «машина» НЕ выдают реквизиты и НЕ участвуют в движении денег.** Приём оплат, выдача реквизитов для перевода и расчёт выполняет только менеджер. Это жёсткое требование заказчика (помечено как критичное).
2. **Идентификатор клиента — `telegram_user_id` (числовой), а не `@username`.** Username в Telegram изменяем и не уникален во времени; он хранится только как отображаемое поле. Вся реферальная привязка идёт по `telegram_user_id`.
3. **Разделение ответственности:** бот ловит и структурирует заявку → менеджер исполняет. Автоматизируется общение и маршрутизация, но не сама сделка.
4. **Реферальные бонусы начисляются после того, как реферал воспользовался продуктом** (совершил сделку), а не по факту регистрации — для защиты от фрода.

## 3. Роли пользователей

| Роль | Описание | Доступ |
|---|---|---|
| Клиент | Пользователь Telegram-бота | Только бот |
| Менеджер | Исполняет заявки, общается с клиентами | Админ-панель |
| Администратор / владелец | Настройки, курсы, %, рассылки, анти-фрод | Админ-панель (полный) |

> ⚠️ Открытый вопрос: точное разграничение прав между менеджером и администратором не финализировано (см. 12).

## 4. Telegram-бот

### 4.1. Главное меню (кнопки)
- Отправить перевод (обмен валют)
- Банковская карта
- Реферальная программа / баланс
- Telegram-группа
- Отзывы
- Правила пользования
- Техподдержка

### 4.2. Обмен валют («Отправить перевод»)

**UX-референс:** механика Wise / «Золотая Корона» — два поля «Что отдаю» / «Что получаю».

**Сценарий (happy path):**
1. Клиент нажимает «Отправить перевод».
2. Появляются два поля/столбца: **Что отдаю** (валюта + сумма) и **Что получаю** (валюта).
3. При выборе валютной пары бот автоматически показывает **предварительный курс**:
   - для **электронного перевода** — курс тянется по API валютной пары, к нему применяется фиксированная комиссия (наценка задаётся в админке);
   - для **наличных** — ставка уточняется менеджером и присылается клиенту **после** подачи заявки.
4. Клиент может **сохранить свои реквизиты** для быстрого получения средств: номер карты, телефон, название банка.
5. При подтверждении заявки бот присылает **уточняющее сообщение**: «Верны ли сохранённые реквизиты?» — клиент подтверждает/правит.
6. Заявка уходит менеджеру в админку с описанием (пример: «клиент отдаёт рубли → хочет получить криптовалюту / на банк в Таиланде / выдачу через банкомат»).
7. Менеджер исполняет сделку вручную; клиент получает **оповещения о смене статуса**.

**Важно:** реквизиты для оплаты клиенту выдаёт менеджер, не бот.

> ⚠️ Открытые вопросы по этому модулю: полный список валютных направлений; фиксируется ли предварительный курс на время (и на сколько); храним ли полный номер карты или маскируем; полный список статусов заявки. См. раздел 12, блок C.

### 4.3. Банковская карта
- Кнопка **«Оставить заявку на открытие европейской карты»**.
- После обработки — в админке отображается статус карты: **активна / отклонена**.
- После открытия карты у клиента появляется кнопка **«Пополнить баланс через менеджера»**.

> ⚠️ Критичный открытый вопрос: выпускаем ли карту сами (через банк-партнёра/BIN-спонсора) или направляем клиента к внешнему провайдеру и только ведём статус. От этого кратно зависит объём работ. См. 12, блок A.

### 4.4. Реферальная программа

- **2 уровня:**
  - 1-я линия — «мой друг» (тот, кого пригласил я);
  - 2-я линия — «друг друга» (кого пригласил мой друг).
- Каждый клиент получает **реферальную ссылку**.
- **Оповещения (пуши):**
  - когда мой реферал зарегистрировался — мне приходит уведомление;
  - когда реферал воспользовался продуктом — мне начисляется установленный процент бонусов;
  - когда мой реферал привёл своего друга — мне приходит пуш «+1 партнёр во 2-й линии».
- В боте отображается: **количество рефералов** (по линиям) и **баланс баллов**.
- **Заявка на вывод:** клиент выводит накопленные баллы на свой счёт — в банк или в криптовалюте, по выбору.
- Реферальный процент **настраивается и изменяется** в админ-панели.

> ⚠️ Открытые вопросы: 1 балл = сколько денег; процент считается от чего (сумма сделки / комиссия / фикс); минимальная сумма вывода; кто исполняет вывод; защита от самореферала. См. 12, блок B.

### 4.5. Техподдержка / AI-консьерж
- Автоматизированное **приветственное общение** с «человеческим» тоном (консьерж).
- База знаний загружается в бота (материалы предоставляет заказчик).
- Задача: принять запрос, структурировать и передать менеджеру заявку с описанием сути обмена.
- Менеджер может **вливаться в диалог**; система анализирует общение и помогает его улучшать.

> ⚠️ Открытые вопросы: поведение при отсутствии ответа (эскалация — куда?); читает ли AI живую переписку менеджера с клиентом (приватность/согласия). См. 12, блок D.

### 4.6. Прочие разделы
- **Telegram-группа** — ссылка/переход.
- **Отзывы** — формат уточняется (лента? ссылка на канал?).
- **Правила пользования** — статический текст.

### 4.7. Рассылки (пуши)
- При регистрации бот спрашивает согласие: **«Можем ли присылать выгодные предложения, новости и акции?»**
- Рассылки отправляются только клиентам, давшим согласие.
- Отправка — из админ-панели.

> ⚠️ Открытый вопрос: только ручные рассылки или ещё триггерные (по статусу сделки и т.п.); механика отписки.

## 5. Админ-панель

- **Заявки на обмен:** просмотр, обработка, смена статусов, оповещение клиента.
- **Курсы и наценки:** настройка процента/комиссии по валютным парам (курс — из API бирж, наценка — вручную).
- **Реферальная система:** настройка процентов по линиям; обработка заявок на вывод.
- **Анти-фрод:** выявление «странного» поведения пользователей (паттерны уточняются).
- **Карты:** ведение статусов заявок на выпуск (активна / отклонена).
- **Рассылки:** отправка пушей клиентам с согласием.
- **Управление менеджерами/ролями.**

> ⚠️ Открытые вопросы: конкретные паттерны анти-фрода (ручной просмотр или авто-блок); полный перечень действий менеджера внутри админки.

## 7. Модель данных (черновая, подлежит уточнению)

Предварительный список сущностей:
- **Client** (`telegram_user_id` — ключ, username, телефон, согласие на рассылку, дата регистрации, реферер).
- **Requisites** (реквизиты клиента: банк, номер карты/телефон — формат хранения уточняется).
- **ExchangeRequest** (заявка: направление, суммы, тип — эл. перевод/нал, статус, менеджер, время).
- **Referral** (связь реферер → реферал, линия 1/2).
- **BonusBalance / BonusTransaction** (начисления и списания баллов).
- **WithdrawalRequest** (заявка на вывод: сумма, способ — банк/крипто, статус).
- **CardApplication** (заявка на карту, статус активна/отклонена).
- **Manager / Role**.

> Финальная схема (поля, связи, индексы) проектируется после закрытия открытых вопросов.

## 8. Интеграции

- **API биржевых курсов** (провайдеры уточняются) — источник курса валютных пар.
- **Крипто-выплаты** — для вывода бонусов и получения крипты (механика уточняется).
- **Партнёр по выпуску карт** — если карта выпускается через внешнего провайдера (см. 12, блок A).
- **CRM** — фаза 2 (см. раздел 10).

---

## 9. Безопасность (принципы; детали — по запросу заказчика)

- Бот не хранит и не выдаёт платёжные реквизиты для оплаты; поверхность риска сужена этим правилом.
- Идентификация клиента по `telegram_user_id`.
- Рекомендация (на согласование): **не хранить полный номер карты клиента**, либо хранить в маскированном виде.
- Требуется защита доступа в админ-панель (аутентификация, роли), rate-limit на заявки/выводы.

> ⚠️ Заказчик просит разработчика предложить варианты модели безопасности. Это возможно **после** ответа по юрисдикции и KYC (раздел 12, блок A) — именно они определяют, что законно хранить и требуется ли верификация.

---

## 10. Этапность

- **Фаза 1 (MVP):** бот (меню, обмен-заявки, реферальная система, карта-заявки, поддержка, пуши) + админ-панель (обработка заявок, курсы, рефералка, рассылки, анти-фрод базово) + сайт.
- **Фаза 2:** интеграция с CRM — метрики поведения, частота покупок, сбор обратной связи, покупательская аналитика.

---

## 11. Требования, ещё не заданные

Нагрузка (число клиентов в первые 3–6 мес.), число одновременно работающих менеджеров, бюджет, сроки, предпочтения по стеку и хостингу, кто поддерживает продукт после запуска — **не определены**.

## 12. Открытые вопросы (БЛОКЕРЫ — закрыть до старта)

### Блок A — Юрисдикция, KYC, природа карты 🔴
- A1. Основная юрисдикция операций (Таиланд / РФ / офшор?) и где находятся клиенты.
- A2. Проводим ли KYC (паспорт/селфи, лимиты для непроверенных) или работаем без верификации.
- A3. «Европейская карта»: выпускаем сами (банк-партнёр/BIN-спонсор) или направляем к внешнему провайдеру и ведём статус.

### Блок B — Экономика реферальной программы 🔴
- B1. 1 балл = сколько денег (привязка к валюте).
- B2. Процент считается от чего (сумма сделки / ваша комиссия / фикс) — с примером на цифрах.
- B3. Вывод: минимальная сумма, кто исполняет, комиссия, срок; источник средств на выплату.
- B4. Начисление за первую сделку друга или за каждую; защита от самореферала.

### Блок C — Механика обмена 🟠
- C1. Полный список валютных направлений для MVP (реальные пары).
- C2. Предварительный курс по эл. переводу — фиксируется на N минут или справочный (финал подтверждает менеджер).
- C3. Хранение реквизитов клиента: полный номер карты или маскированный.
- C4. Полный список статусов заявки и кто какой статус ставит.

### Блок D — Поддержка, сайт, эксплуатация 🟡
- D1. AI-консьерж: поведение при незнании ответа (эскалация куда); читает ли AI живую переписку менеджера.
- D2. Сайт: лендинг или веб-сервис; готов ли брендинг.
- D3. Число менеджеров и клиентов (3–6 мес.), бюджет, срок, стек/хостинг, поддержка после запуска.

## 13. Оценка готовности

| Раздел | Статус | Комментарий |
|---|---|---|
| Бизнес-логика | ⚠️ | Форма продукта ясна; экономика рефералки и детали обмена — нет |
| UX | ⚠️ | Есть референс (Wise) и флоу обмена; состояния прочих экранов не описаны |
| Backend | ⚠️ | Разделение «бот ловит → менеджер исполняет» задано; статусы и модели — нет |
| Frontend / сайт | ❌ | Не решено: лендинг или веб-сервис |
| API | ⚠️ | Курсовой API + наценка концептуально; провайдеры и фиксация курса — нет |
| База данных | ❌ | Черновой список сущностей; поля/связи/хранение реквизитов не финализированы |
| Безопасность | ⚠️ | Бот не трогает деньги — плюс; KYC, данные карты, доступ в админку — нет |
| Edge Cases | ❌ | Не рассмотрены |
| Ошибки | ❌ | Обработка не описана |
| Производительность | ⚠️ | Масштаб малый, исполнение ручное — пока не риск |
| Интеграции | ⚠️ | Названы концептуально (курсы, крипто-выплаты, карта) |
| Юр. соответствие | ❌ | Мультиюрисдикция (РФ / Таиланд / крипта / EU-карта) — главный пробел |

**Готовность ТЗ к разработке: ~32%.**
Документ пригоден для созвона и предварительной оценки, но **не** для старта разработки — сначала закрываются блокеры раздела 12 (в первую очередь блоки A и B).
